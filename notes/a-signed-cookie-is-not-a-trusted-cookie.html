A Signed Cookie Is Not a Trusted Cookie

The cookie that carried its own key

Google's developer documentation sites share an OAuth flow. You hit /oauth2authorize, it sets a Flask session cookie and sends you to Google's sign-in page, and no account is needed to make it happen. A security researcher mapping that flow noticed the cookie was about 1,200 bytes, which is a lot of room for a CSRF token and a return URL.

Flask session cookies are signed, not encrypted. Anyone holding one can read what is inside it, and what was inside this one was a pickled oauth2client flow object with Google's OAuth client_id and client_secret sitting in plaintext. The leading dot on the payload meant it was zlib-compressed, which is why it decoded cleanly.

Then came the part that turned a leak into a vulnerability. The client secret, tried as the Flask SECRET_KEY, validated the signature on the cookie Google had just issued. The signing key was stored inside the object it signs.

Why signing is not a boundary

Signed and trustworthy are different properties, and the design treated one as if it implied the other. Signing is an integrity check. It tells you the payload was not edited after the server wrote it. It says nothing about who can read the payload, and nothing about whether the payload is safe to load.

Flask signs through itsdangerous using the cookie-session key derivation, so the signature is reproducible offline from the key. Recomputed that way, it came out byte-for-byte identical to the signature on the cookie. One flipped character was rejected, and re-signing the original payload with the recovered secret was accepted. Session integrity was gone. Any key and value could be set, and the server would still take the cookie.

The OAuth callback then read the flow object back out of the session and unpickled it. That pickle.loads is only safe while nobody else can forge a valid cookie, and the key was public. Python's own documentation states the rule without hedging: the pickle module is not secure, it is possible to construct malicious pickle data which will execute arbitrary code during unpickling, and data that could have come from an untrusted source or been tampered with should never be unpickled. The REDUCE opcode names a callable and its arguments, and unpickling calls it. A public signing key plus that sink is unauthenticated remote code execution.

What the proof of concept did

No commands were run against production. The payload was reduced to time.sleep(N) and the response time tracked the number in the pickle. Zero seconds of sleep returned in 0.207s, three in 3.193s, five in 5.194s, eight in 8.283s.

The controls matter more than the timing. No cookie came back Invalid request. One flipped byte in the signature came back Invalid request. A valid signature with no matching flow entry came back Invalid request state. A valid signature with the real flow reached Google's token exchange and failed later on the fake authorization code. Only the forged session with the sleep payload was delayed by exactly the number chosen.

How far one key reached

This was not a single application. It was the shared DevSite platform, so the key from developers.google.com also signed valid sessions on firebase.google.com, developer.android.com, source.android.com and docs.partner.android.com.

The timeline is short. The report went in on August 6, was triaged and accepted on August 7, the reward was decided on August 27 at $90,000 (a $75,000 base for an S0 remote code execution, multiplied by 1.2 for report quality), and the fix shipped on October 7.

The four fixes, and why they stack

  1. Rotate both exposed OAuth client secrets and kill every session signed with them.
  2. Give each deployment its own high-entropy Flask SECRET_KEY from a server-side store, with nothing to do with an OAuth credential.
  3. Keep the OAuth flow object on the server. The cookie should hold an opaque reference and nothing sensitive.
  4. Drop pickle for anything crossing a client boundary. A data-only format with a schema check makes a forged cookie inert.

Any one of those four breaks the chain. That is the useful part of the writeup, and it is also the uncomfortable part, because the chain depended on all four being absent at once.

What to check in your own stack

Three questions, and none of them needs a security team.

Is any signing key in your stack also a credential that gets handed to a third party? The Flask SECRET_KEY and the OAuth client secret were the same string, which is what made the leak fatal rather than embarrassing.

Does any session cookie carry a serialized object rather than an identifier? The cookie should hold an opaque reference and nothing sensitive, and a session store on the server is the cheap way to get there.

Is pickle.loads reachable from anything a request can influence? Python's documentation suggests signing data with hmac when tamper detection is the goal, and notes that deserializing untrusted JSON does not in itself create an arbitrary code execution vulnerability. If the answer is yes and the data crosses a trust boundary, the format is the bug.

Signing proves the payload was not edited on the way in. It says nothing about who can read it, and a secret that can be read is a secret that has been published.
