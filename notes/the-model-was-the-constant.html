The Model Was the Constant

What harness engineering is

LangChain's coding agent went from Top 30 to Top 5 on Terminal Bench 2.0. The model never changed. The harness did.

That result inverts the usual reflex, which is to reach for a bigger model when an agent underperforms. LangChain kept gpt-5.2-codex fixed, changed the system prompt, the tools and the middleware, and moved deepagents-cli 13.7 points, from 52.8 to 66.5. Terminal Bench 2.0 has 89 tasks across machine learning, debugging and biology, orchestrated with Harbor on Daytona sandboxes and traced in LangSmith.

Their own definition of the discipline is compact. The goal of a harness is to mold the inherently spiky intelligence of a model for tasks we care about. Harness engineering is about systems, building tooling around the model to optimize goals like task performance, token efficiency and latency.

An agent harness has a lot of knobs. System prompts, tools, hooks and middleware, skills, sub-agent delegation, memory systems. LangChain deliberately compressed the optimization space to three of them: the system prompt, the tools, and middleware, which is their word for hooks around model and tool calls.

The failure the harness had to fix

The most common failure pattern in their traces was that the agent wrote a solution, re-read its own code, confirmed it looks ok, and stopped.

That is a recognition failure, not a capability failure. Self-verification allows agents to self-improve via feedback within a run, but they don't have a natural tendency to enter this build-verify loop. Something outside the model has to force it.

Their fix is a middleware hook. A PreCompletionChecklistMiddleware intercepts the agent before it exits and reminds it to run a verification pass against the Task spec. The system prompt carries the same demand as four steps: plan and discover, build with tests for happy paths and edge cases, verify against the task specification, then fix. LangChain compares the hook to a Ralph Wiggum Loop, where a hook forces the agent to continue executing on exit. Geoffrey Huntley's version of that pattern is a single process in a single repository, one task per loop, with the loop itself treated as the unit of engineering.

One line in those four steps is doing more work than the other three. The agent is told to compare test output against what was asked, not against its own code. Verifying against its own code is exactly what it was already doing when it stopped.

Context is delivered, not discovered

Two more hooks do work that has nothing to do with intelligence.

A LocalContextMiddleware runs on agent start to map the working directory and its parent and child directories, and runs bash commands to find tools like Python installations. Context discovery and search are error prone, so injecting the answer reduces the error surface and onboards the agent into its environment.

A LoopDetectionMiddleware tracks per-file edit counts through tool call hooks and adds a suggestion to reconsider the approach after N edits to the same file. The failure it targets is a doom loop, meaning small variations on the same broken approach, 10 or more times in some traces. The nudge helps and does not guarantee anything. The model can continue down the same path if it thinks it is correct.

Time budgeting is injected as well. Agents are famously bad at time estimation, so warnings that nudge the agent to finish and shift to verification are the only thing standing between a task set with timeouts and a harness that respects them.

More reasoning is not more score

The counterintuitive result is about compute. gpt-5.2-codex has four reasoning modes, low, medium, high and xhigh. Running only at xhigh scored 53.9%, worse than 63.6% at high, because agents timed out. More reasoning helps agents evaluate each step, but can burn over 2x more tokens and time.

Their baseline became a split across the run, xhigh for planning, high in the middle, xhigh again for verification. That combination pushed the score to 66.5%.

The lesson generalizes past this benchmark. A reasoning budget is a harness parameter. Treating the maximum setting as the default is a way to spend more and finish less, and the cost shows up as timeouts rather than as bad answers.

Traces are the feedback loop

None of the changes above were designed from first principles. They were read off traces.

LangChain turned the process into a skill: fetch experiment traces, spawn parallel error analysis agents, have a main agent synthesize the findings and suggestions, then make targeted changes to the harness. The authors compare it to boosting, which concentrates on mistakes from previous runs. They also name the risk, that changes which overfit to a task are bad for generalization and can lead to regressions in other tasks.

One of their own results supports the caution. A test run with Claude Opus 4.6 scored 59.6% with an earlier harness version, competitive but worse than Codex, because the same improvement loop had not been run for Claude. The harness had been fitted to one model.

What the numbers do not say

The improvement is real and measured. It is also narrow. 89 tasks, one benchmark, one model, one team's iteration budget.

Two hedges belong next to the result, both from the authors. The middleware guardrails are described as a design heuristic that engineers around today's perceived model issues, and as models improve, these guardrails will likely be unnecessary. Blind retries and missing verification are their examples of the patterns expected to dissolve.

The tuning is not portable by default either. LangChain's closing point is that models require different prompting, and the general principles travel better than any specific hook.

What to change this week

Three moves, and none of them needs a new model.

Add an exit check. Something in the loop that refuses to let the agent finish before it has run the tests and compared the output to the specification. It is the highest-return change in the post and it is a hook rather than a prompt rewrite.

Measure the reasoning budget instead of maximizing it. Run the middle setting and the top setting on your own task set, and compare completion rates rather than quality on the tasks that happened to finish.

Read your own traces before changing anything. The failure modes that matter are the ones your agent actually produces. The LangChain list, reasoning errors, ignored instructions, missing tests, running out of time, is a starting checklist rather than an answer.

Most of what moved the score was code a team can write itself.
