The Modern Python Developer’s Trap: When Code Looks Right but Isn’t

AI can produce Python faster than ever. It cannot verify the assumptions, architecture, performance characteristics, or security boundaries hidden inside that code.

Python has always rewarded developers who understand how the language actually behaves. That matters even more now that code can be produced by humans, autocomplete systems, and autonomous coding agents.

The source of the code has changed. The failure modes have not.

A generated function can still misuse a data structure. An agent can still introduce an N+1 query. A developer can still swallow an exception, leak a resource, or build an abstraction nobody needs. The difference is that AI-assisted development makes it possible to introduce more code, across more files, at a higher speed.

That changes the engineering problem.

The important question is no longer simply whether code can be produced quickly. It is whether the developer can verify what that code assumes, what it changes, what it depends on, and how it behaves when reality differs from the happy path.

This is a collection of common Python and development-workflow traps viewed through that lens.

1. Python Has Sharp Edges

Some Python mistakes are not syntax mistakes. The code is perfectly valid Python. The problem is that the developer has misunderstood one of the language's semantics or chosen an operation that does not match the problem.

These mistakes are particularly easy for AI-assisted development to reproduce because a language model can generate idiomatic-looking code without necessarily understanding the invariant the code must preserve.

Don't Check What You Are About to Do Unless the Check Matters

Python's EAFP style, "Easier to Ask Forgiveness than Permission," is often misunderstood.

It does not mean "always use exceptions."

It means that when the operation itself provides a reliable way to determine whether something can be done, it can be clearer to perform the operation and handle the expected failure than to perform a separate pre-check.

Consider a dictionary lookup:

def process_user_data(user_record: dict[str, str]) -> str | None:
    """Return a normalized email address when one is present."""
    if "email" not in user_record:
        return None

    return user_record["email"].lower()

This is perfectly reasonable code. There is no need to replace every if with a try block simply because Python supports EAFP.

But if the operation is already the thing you need to perform, a pre-check can be unnecessary:

def get_email(user_record: dict[str, str]) -> str:
    """Return a normalized email address or raise KeyError if it is absent."""
    return user_record["email"].lower()

The caller can handle the missing key if that is an expected condition:

try:
    email = get_email(user_record)
except KeyError:
    email = None

There is another option when a missing value is part of the normal contract:

def get_email(user_record: dict[str, str]) -> str | None:
    """Return a normalized email address when the field exists."""
    email = user_record.get("email")
    return email.lower() if email is not None else None

The choice depends on the contract.

  • Use .get() when a missing key naturally means "no value."
  • Use try/except when the operation is expected to succeed and the exception represents a condition the caller can handle.
  • Use an explicit membership check when the distinction between "missing" and "present" matters before the lookup.

The anti-pattern is not the if. The anti-pattern is performing defensive checks mechanically without considering the operation's actual contract.

Choose the Data Structure for the Operation

A list is a sequence. It is not a universal lookup table.

This becomes expensive when membership testing happens repeatedly:

def filter_users(
    all_users: list[str],
    banned_users: list[str],
) -> list[str]:
    """Return users who are not present in the banned-user list."""
    return [
        user
        for user in all_users
        if user not in banned_users
    ]

If there are N users and M banned users, each membership test can scan the list. In the worst case, the work is proportional to N × M.

For repeated membership tests, a set is normally more appropriate:

def filter_users(
    all_users: list[str],
    banned_users: list[str],
) -> list[str]:
    """Return users who are not present in the banned-user set."""
    banned = set(banned_users)

    return [
        user
        for user in all_users
        if user not in banned
    ]

Building the set costs O(M). Average-case membership testing in a hash table is O(1), so the expected total work becomes O(N + M).

Choose the data structure based on the operation you perform most often.

A large percentage of performance problems are not caused by exotic algorithms. They come from using a reasonable data structure for the wrong job.

is Tests Identity. == Tests Equality.

This mistake is common because some incorrect is comparisons appear to work.

def check_status(status: str) -> bool:
    """Return whether status contains the expected value."""
    return status is "COMPLETED"

That is wrong.

is tests object identity. It asks whether two expressions refer to the same object. == tests equality. It asks whether two objects compare as equal. 

def check_status(status: str) -> bool:
    """Return whether status contains the expected value."""
    return status == "COMPLETED"

Object identity is appropriate when identity itself has meaning. The classic example is None: 

def has_value(value: str | None) -> bool:
    """Return True when value is not the None singleton."""
    return value is not None

You will sometimes see is appear to work with integers or strings because of implementation details such as object interning. That behavior should never be used as a value-comparison mechanism.

If the question is "does this value equal that value?", use ==. If the question is "is this the exact same object?", use is.

Let Context Managers Own Resources

Resource ownership should be explicit.

def read_log_data(filepath: str) -> str:
    """Read a text file and return its contents."""
    file = open(filepath, encoding="utf-8")
    data = file.read()
    file.close()

    return data

If read() raises an exception, close() is never reached.

The context manager protocol exists to solve exactly this problem:

def read_log_data(filepath: str) -> str:
    """Read a UTF-8 text file and close it when the operation finishes."""
    with open(filepath, encoding="utf-8") as file:
        return file.read()

The with statement ensures that the file is closed when control leaves the block, including when the block exits because of an exception or an early return.

The same ownership principle applies to:

  • files
  • database connections
  • locks
  • temporary files
  • network clients
  • transactions

Who owns this resource, and what mechanism guarantees that ownership ends correctly?

Mutable Default Arguments Are Persistent State

def append_event(
    event: str,
    timeline: list[str] = [],
) -> list[str]:
    """Append an event to the supplied timeline."""
    timeline.append(event)
    return timeline

The default list is created when the function definition is evaluated, not each time the function is called. 

print(append_event("start"))
print(append_event("stop"))

This produces:

['start']
['start', 'stop']

The usual solution is a None sentinel:

def append_event(
    event: str,
    timeline: list[str] | None = None,
) -> list[str]:
    """Append an event to a new or supplied timeline."""
    if timeline is None:
        timeline = []

    timeline.append(event)
    return timeline

This is not merely a style preference. It follows directly from Python's function-definition semantics.

Don't Shadow Built-in Names

def format_records(list, input):
    """Format records using a supplied value."""
    dict = {}

    for item in list:
        dict[item] = input

    return dict

list, input, and dict are built-in names. Assigning to them shadows the built-ins in the relevant scope. 

def format_records(
    records: list[str],
    input_value: str,
) -> dict[str, str]:
    """Map each record to the supplied input value."""
    return {
        record: input_value
        for record in records
    }

Name the thing according to its role, not merely its Python type.

2. Code That Doesn't Survive Growth

Python makes it easy to start small. That is a strength. The problem begins when developers preserve the structure of a prototype while adding production responsibilities to it.

The Script-to-Monolith Problem

A growing script often accumulates:

  • configuration
  • API calls
  • validation
  • business rules
  • persistence
  • logging
  • retries
  • error handling

The problem is not that this code lives in one file. The problem is that several responsibilities become coupled together.

from dataclasses import dataclass
import sqlite3


@dataclass(frozen=True)
class Sale:
    """Represent a calculated sale value."""

    value: float


def calculate_sale_value(amount: float, rate: float = 0.15) -> float:
    """Apply the configured rate to an amount."""
    return amount * (1 + rate)


def save_sale(database_path: str, sale: Sale) -> None:
    """Persist a sale in the SQLite database."""
    with sqlite3.connect(database_path) as connection:
        connection.execute(
            "INSERT INTO sales (value) VALUES (?)",
            (sale.value,),
        )

The useful form of separation is to make dependencies visible and isolate behavior that can be tested independently.

Folder structure is not architecture. Dependency boundaries are.

Don't Build an Architecture for Problems You Don't Have

There is nothing technically wrong with an interface and provider abstraction. The question is whether the abstraction is buying anything. 

from abc import ABC, abstractmethod


class NotificationProvider(ABC):
    """Define the interface for notification providers."""

    @abstractmethod
    def send(self, message: str) -> None:
        """Send a notification."""
        raise NotImplementedError


class EmailNotificationProvider(NotificationProvider):
    """Send notifications by email."""

    def send(self, message: str) -> None:
        print(f"Sending email: {message}")
def send_email_notification(
    message: str,
    recipient: str,
) -> None:
    """Send a notification to one recipient."""
    if "@" not in recipient:
        raise ValueError("Invalid recipient email address")

    print(f"Sending email to {recipient}: {message}")

Introduce abstraction to protect a real boundary or a meaningful variation, not an imaginary future requirement.

Make Dependencies Reproducible

uv init my_project
cd my_project

uv add flask requests pydantic
uv lock

The important distinction is between declaring requirements and reproducing a tested environment.

A production build should come from a known dependency resolution, not whatever versions happen to be current when a server is provisioned.

Every dependency is additional code that your application executes or trusts. Do not add a package simply because an AI assistant suggested an import.

3. AI Changes the Failure Rate, Not the Laws of Software

AI coding assistants and agents change the economics of writing software. They also change the cost of accepting a bad decision.

When an agent changes multiple files, adds a dependency, modifies a data model, and introduces helper functions, line-by-line familiarity becomes a poor substitute for verification.

Don't Treat Generated Code as Verified Code

def update_user_profile(user_id, raw_payload):
    """Update a user profile from untrusted input."""
    data = eval(raw_payload)

    db.execute(
        f"UPDATE users SET info = '{data}' WHERE id = {user_id}"
    )

This contains multiple problems:

  • eval() executes arbitrary Python expressions.
  • The input is not validated against a schema.
  • SQL is constructed through string interpolation.
  • The database dependency is implicit.
  • The authorization boundary is not visible.
from pydantic import BaseModel, EmailStr


class UserProfile(BaseModel):
    """Represent the fields accepted by a profile update."""

    name: str
    email: EmailStr


def update_user_profile(
    database,
    user_id: int,
    raw_payload: str,
) -> None:
    """Validate profile input and update the corresponding user."""
    profile = UserProfile.model_validate_json(raw_payload)

    database.execute(
        """
        UPDATE users
        SET name = :name, email = :email
        WHERE id = :id
        """,
        {
            "name": profile.name,
            "email": profile.email,
            "id": user_id,
        },
    )

Structured code does not automatically prove the operation is secure. Authorization, transactions, and database behavior still need to be verified.

Don't ask only: "Does this code run?" Ask: "What assumptions does it make?"

Give Agents Repository Context

An agent working from a small snippet can only reason about the information it can see. 

# Repository conventions

## Logging

Use `src.core.logger.logger` for application logging.
Do not create module-level logging configuration.

## Validation

Use Pydantic v2 models for externally supplied structured data.

## Formatting

Run Ruff before committing.

## Dependencies

Do not introduce a third-party package when the standard library
or an existing project dependency provides the required functionality.

Repository instructions are only one form of context. Tests, type definitions, existing abstractions, configuration, and CI rules also communicate how the system is expected to behave.

If an architectural rule matters, it should not exist only in someone's memory.

Watch for Hallucinated Dependencies

from json_helpers import parse_json

The import looks plausible. That is not evidence that the package or API exists.

Before adding a package:

  1. Verify that the package exists.
  2. Confirm that it is the intended project.
  3. Check whether the standard library already solves the problem.
  4. Check whether the repository already has an equivalent dependency.
  5. Review whether the dependency is actually necessary.
  6. Use a reproducible dependency resolution.

AI can suggest dependencies. It should not get to decide what your software supply chain contains.

4. Performance Problems Usually Start as Reasonable Code

Performance bugs often survive code review because the implementation is logically correct. The problem appears only when the operation is repeated, concurrent, or applied to a larger dataset.

Don't Block an Async Event Loop

import time
import requests


async def fetch_dashboard_data() -> dict:
    """Fetch dashboard statistics."""
    time.sleep(2)

    response = requests.get(
        "https://api.example.com/stats",
        timeout=10,
    )

    return response.json()

time.sleep() blocks the thread. requests.get() performs synchronous I/O. 

import httpx


async def fetch_dashboard_data(client: httpx.AsyncClient) -> dict:
    """Fetch dashboard statistics without blocking the event loop."""
    response = await client.get(
        "https://api.example.com/stats",
        timeout=10,
    )
    response.raise_for_status()

    return response.json()

The client is passed into the function rather than created for every request so its lifetime and connection reuse can be managed at the appropriate application boundary.

async def does not make blocking operations non-blocking.

Watch for N+1 Queries

orders = Order.objects.all()

for order in orders:
    print(order.customer.name)

If customer is lazily loaded, the application can issue one query for the orders and additional queries as individual customers are accessed. 

orders = Order.objects.select_related("customer")

for order in orders:
    print(order.customer.name)

Django's select_related() and prefetch_related() solve different relationship-loading problems. The latter generally performs separate queries and combines the results in Python rather than simply issuing one SQL join.

Don't let a loop determine your database query count accidentally.

Build Strings According to the Work You Are Doing

def build_report(rows: list[str]) -> str:
    """Build a newline-delimited report."""
    report = ""

    for row in rows:
        report += row + "\n"

    return report

A clearer approach when assembling many fragments is to join the pieces:

def build_report(rows: list[str]) -> str:
    """Build a newline-delimited report."""
    return "".join(f"{row}\n" for row in rows)

Or, when a trailing newline is unnecessary:

def build_report(rows: list[str]) -> str:
    """Build a newline-delimited report."""
    return "\n".join(rows)

The point is not that repeated += is universally quadratic. Python implementations can optimize some concatenation patterns. The stronger recommendation is to use join() when deliberately assembling many fragments rather than relying on implementation-specific behavior.

5. Small Style Mistakes Become Expensive at Scale

Some practices do not usually bring down a production system by themselves. They do make code harder to inspect, understand, refactor, and automate.

Avoid Wildcard Imports

from math import *
from numpy import *

result = sqrt(16)

The source of sqrt() is unclear.

import math
import numpy as np


standard_result = math.sqrt(16)
array_result = np.sqrt(np.array([16, 25]))

Explicit namespaces help readers, IDEs, static analyzers, refactoring tools, and AI coding agents reconstruct where a symbol comes from.

Catch the Exception You Can Actually Handle

try:
    value = int(input("Enter a number: "))
except:
    print("Invalid input")

A bare except catches exceptions derived directly from BaseException, including KeyboardInterrupt and SystemExit. 

try:
    value = int(input("Enter a number: "))
except ValueError:
    print("Invalid numerical input.")
  1. Catch the specific exception you can handle.
  2. Catch a meaningful exception family when appropriate.
  3. Catch Exception at deliberate boundaries when the application needs to log, translate, retry, or terminate an operation.
  4. Almost never catch BaseException.

6. The Better AI Workflow Is Verification, Not Better Prompting

Prompt quality matters. Repository context matters. Neither substitutes for verification. 

Intent
  ↓
Generated implementation
  ↓
Tests
  ↓
Static analysis
  ↓
Type checking
  ↓
Dependency/security checks
  ↓
Diff review
  ↓
CI
  ↓
Deployment

Each layer catches a different class of failure.

Tests

Tests ask whether known behavior works. They are useful for edge cases, regression protection, business rules, error behavior, and integration boundaries.

Tests can only protect behavior you have actually specified.

Type Checking

A type checker can catch mismatched interfaces and inconsistent assumptions. It cannot prove business correctness, authorization, or architectural suitability.

Linting and Formatting

Tools such as Ruff catch many classes of style and static-analysis problems. Formatting removes an entire category of human debate. Neither understands your application's business invariants.

Dependency Controls

Locking and dependency review improve reproducibility and reduce unnecessary changes to the software supply chain. They do not tell you whether a dependency is architecturally justified.

Repository Instructions

Files such as AGENTS.md, project documentation, and contributor guidelines give AI systems useful constraints. They do not enforce those constraints. Tests and CI provide the enforcement mechanism.

Human Review

Some questions remain contextual:

  • Is this the correct abstraction?
  • Does this preserve the application's invariants?
  • Is the transaction boundary correct?
  • Is authorization enforced at the right point?
  • Does this change fit the architecture?
  • Is the new dependency justified?
  • What happens when this code runs concurrently?
  • What happens when the dataset is 100 times larger?

AI can accelerate implementation. It does not remove the need to answer those questions.

7. A Practical Review Checklist for AI-Generated Python

When reviewing generated or heavily AI-assisted code, do not limit the review to whether the diff looks clean.

Correctness

  • Does the implementation satisfy the actual requirement?
  • What assumptions does it make about its inputs?
  • What happens when those assumptions are false?
  • Are edge cases represented by tests?
  • Does the error behavior match the application's contract?

Python Semantics

  • Are is and == being used correctly?
  • Are mutable defaults avoided?
  • Are resources managed through context managers where appropriate?
  • Are built-in names being shadowed?
  • Are exceptions specific enough?
  • Is the chosen data structure appropriate for the operation?

Architecture

  • Does the change introduce a new dependency boundary?
  • Does it bypass an existing abstraction?
  • Has business logic become coupled to I/O?
  • Has a small feature acquired unnecessary layers?
  • Is configuration still isolated from application behavior?

Dependencies

  • Did the agent introduce a new package?
  • Does the package actually exist?
  • Is it necessary?
  • Is the repository already solving the same problem?
  • Is the resolved dependency set reproducible?

Performance

  • How many database queries does this execute?
  • Is work being repeated unnecessarily?
  • What happens as the input grows?
  • Is a blocking operation running in an async context?
  • Is memory usage proportional to the amount of data being processed?

Security

  • Is untrusted data crossing a trust boundary?
  • Is input validated?
  • Is SQL parameterized?
  • Is arbitrary code execution possible?
  • Are authorization checks present?
  • Did the generated code introduce a new attack surface?

AI-Specific Questions

  • Did the agent invent a helper that already exists?
  • Did it introduce a library the project does not use?
  • Did it follow repository conventions?
  • Did it modify files outside the intended scope?
  • Did it make assumptions that were not present in the task?
  • Did it preserve existing tests and interfaces?
  • Can you explain every significant part of the diff?

If a developer cannot explain a generated change, the change has not really been reviewed.

Conclusion: Code Generation Is Cheap. Verification Is the Engineering Work.

Python has not become harder because AI can write it. In some respects, Python has become easier to produce.

The difficult part has moved.

A developer who writes every line personally still needs to understand Python's object model, resource management, data structures, concurrency model, database behavior, and architectural boundaries.

A developer who delegates implementation to an AI agent needs to understand those things too.

The difference is that the second developer can now introduce mistakes much faster.

The most dangerous generated code is not code that obviously looks broken. It is code that looks reasonable, passes a simple test, follows familiar conventions, and quietly violates an assumption somewhere else in the system.

That is why the useful question during code review is not:

"Did the AI write this correctly?"

It is:

What does this code assume, and how have we verified those assumptions?

That question works for manually written Python, autocomplete-generated functions, and autonomous coding agents alike.

The tools will continue to change. The engineering obligations will not.
