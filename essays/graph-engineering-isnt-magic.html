Graph Engineering Isn’t Magic: It’s Just Loops with State Management

A graph-based agent can look complicated when you first encounter one. You see nodes, state objects, routing functions, checkpoints, and framework APIs.

Most agent workflows can be understood as repeated execution: run an operation, update state, inspect the result, and decide what happens next. This article follows that progression from plain Python to explicit state management and graph-based execution.

The Loop and the State

Consider a coding agent that generates a function, runs tests, examines failures, and repairs the implementation.

The workflow loop is straightforward:

The repeated part is the actual loop the agent moves around while it generates and tests the code.

A small implementation of this loop could be:

attempts = 0

while attempts < 3:
    result = run_tests(code)

    if result.passed:
        break

    code = repair_code(
        code=code,
        error=result.error,
    )

    attempts += 1

The program runs an operation, checks its result, and either stops or runs another operation.

The other part is the state the workflow carries between iterations.

The State

At first, the program only needs the generated code. Once testing and repair are added, it needs to retain the latest result and error:

state = {
    "code": code,
    "test_result": None,
    "error": None,
    "attempt_count": 0,
}

A slightly larger workflow might need:

  • code
  • test_result
  • error
  • attempt_count
  • messages
  • status

Each field exists because a different part of the system depends on it. code is the current working artifact that every step reads and updates. test_result captures the latest execution outcome so the system does not need to rerun tests just to inspect past results. error stores the most recent failure context, which is what the repair step uses to decide what to change.

attempt_count tracks how many iterations have occurred so the workflow can enforce retry limits or switch strategies after repeated failures. messages preserves any accumulated interaction or tool output that may be required for debugging or for the model to maintain continuity. status represents the current phase of execution, such as running, repairing, or completed, and is often used for routing or external visibility.

The repair step needs the current code and the latest error. The retry policy needs the attempt count. Logging may need the previous test result. A user interface may need the current status.

The loop is still doing the execution. The state carries information from one step to the next. As such, the loop controls execution. State records the information required to continue execution.

State Is Not the Same as Message History

In a basic LLM application, much of the state may live in a message list:

messages = [...]

That is useful when the main requirement is giving the model the conversation it needs.

It becomes less convenient when the application needs structured information such as:

state = {
    "code": "...",
    "test_result": "...",
    "error": "...",
    "attempt_count": 2,
    "status": "repairing",
}

Now the application can read the current attempt count directly. It does not need to infer it from previous messages.

As workflows grow, reconstructing application state from message history becomes harder to test and maintain.

Once retry logic, tool calls, and branching behavior are introduced, relying on message history to reconstruct state becomes fragile. You have to scan or interpret past events to determine “where you are” in the process, which can lead to subtle bugs when messages are reordered, truncated, or partially lost. With explicit state, the workflow can make decisions deterministically based on a single source of truth, such as attempt_count, rather than reconstructing intent from a sequence of past interactions.

Suppose the agent has generated three versions of a function, run five tests, received two tool results, found a security warning, and is waiting for approval. Some information needs to be available to the model. Some need to be available to the application. The same piece of information may need to exist in both.

The state object holds the current values. The schema defines which fields the workflow expects and what type of value each field contains.

A state model gives the application a place to represent information that must persist across steps in the workflow instead of being inferred from local variables or message history. This becomes important once multiple operations need to read and update the same shared context.

For example, in a simple code-generation and testing loop, the workflow needs to track the current code, the latest test result, any error output, how many attempts have been made, and the current execution status. This is usually implemented in a key:value pair structure, such as the following dictionary:

from typing import TypedDict


class AgentState(TypedDict):
    code: str
    test_result: str
    error: str | None
    attempt_count: int
    status: str

Each field corresponds to a piece of information that would otherwise be scattered across function scope, loop variables, or reconstructed from history. Keeping it in a single state object makes updates explicit and makes it clear what data is carried from one step to the next.

The exact fields will vary by application. The important part is deciding what the workflow actually needs to remember and representing that information deliberately.

The Same Agent, Three Ways

The easiest way to see why these abstractions exist is to keep the application behavior the same while changing only how it is implemented. If the requirements do not change, but the structure of the code does, it becomes much easier to see what each abstraction is actually buying us in terms of clarity, control, and state management.

To make this concrete, consider the simple code agent I mentioned earlier. It stays the same across all implementations, but it has five requirements:

  1. Generate a Python function from a specification.
  2. Run tests against the generated function.
  3. Use test failures to repair the function.
  4. Allow up to three attempts.
  5. Escalate to human review after the retry limit.

These requirements stay the same throughout the three stages I will demonstrate below.

Stage 1: The Raw while Loop

The first version uses a simple Python while loop.

def run_code_agent():
    code = ""
    error_feedback = ""
    retries = 0
    max_retries = 3
    tests_passed = False

    while not tests_passed and retries < max_retries:

        if error_feedback:
            code = repair_code(
                code=code,
                error=error_feedback,
            )
        else:
            code = generate_code()

        result = run_tests(code)

        if result.passed:
            tests_passed = True
        else:
            error_feedback = result.error
            retries += 1

    if tests_passed:
        return code

    return "Escalate to human review"

The control flow is visible. The state is local. Each step in the loop directly maps to a concrete action: generate code, run tests, check the result, and either exit or update the code based on the failure. The execution path is linear and easy to follow because all decisions are made in one place.

You can trace the entire execution by reading one function, from initial code generation through repeated test-and-repair cycles until success or the retry limit is reached.

Suppose the agent also needs to search documentation for unfamiliar errors, run a security check, use a different repair strategy after repeated failures, and wait for human approval before applying a risky change.

This agent can still handle these complications within the workflow. The change is that the main loop simply starts accumulating more responsibilities.

while not tests_passed and retries < max_retries:

    if needs_documentation(error_feedback):
        documentation = search_docs(error_feedback)

    if security_check_required(code):
        security_result = run_security_check(code)

    repair = generate_repair(
        code=code,
        error=error_feedback,
        documentation=documentation,
    )

    if requires_human_review(repair):
        approved = request_human_review(repair)

        if not approved:
            continue

    code = apply_repair(repair)

The individual operations are still easy to understand. The execution logic around them is getting harder to follow.

That distinction matters because it separates what the system remembers (state) from how it moves forward (control flow). If you don’t separate them, logic and data get mixed together, making the workflow harder to reason about, debug, and most importantly, extend.

Stage 2: The ReAct Loop

A ReAct-style workflow moves some of the decision-making about which tool or action to run next from fixed application logic into the model itself.

The basic cycle becomes:

User request
    ↓
   LLM
    ↓
Choose action
    ↓
Tool execution
    ↓
Tool result
    ↓
   LLM
    ↓
Choose next action
    ↓
   ...

A simplified implementation looks like this:

messages = [user_request]

while True:
    response = model.generate(messages)

    messages.append(response)

    if response.is_final:
        return response

    result = execute_tool(response.tool_call)
    # Assume the model returns at most one tool call per turn

    messages.append(result)

The Python loop still controls repeated execution. The model now supplies some of the decisions that determine which tool or action runs inside that loop. The difference is that the model now participates in deciding which operation to run, rather than the application code fully determining the next step through fixed conditions.

In the Stage 1 version, the programmer writes:

if result.passed:
    finish()
else:
    repair_code(...)

In a ReAct-style system, the model might decide to:

test failed
    ↓
   LLM
    ├── search documentation
    ├── repair code
    ├── run another test
    └── finish

That gives the workflow more flexibility. It also means that some control decisions are now model-driven rather than fixed in application code.

That has consequences.

The model may choose an unexpected action. It may repeat a tool call. It may stop without performing an operation that the application considers mandatory. It may also hallucinate a tool result or confidently produce reasoning that is not grounded in any actual execution, which can lead the workflow down a completely invalid path if the system treats the output as authoritative.

There is also a more subtle issue: the model making the decision is often not the same model that performs the heavy reasoning or has the strongest capabilities. In practice, a smaller or cheaper model is frequently used to decide what to do next, while a more capable model is reserved for generation or repair steps. This creates a mismatch where a less powerful model is responsible for routing complex reasoning tasks, and it may not reliably understand when it is appropriate to escalate, retry, or request additional context.

The application still needs limits and checks around those decisions.

There is also a state-management problem.

The message history may grow like this:

User request
↓
Generated code
↓
Test tool call
↓
Test output
↓
Repair decision
↓
Documentation lookup
↓
Documentation result
↓
New code
↓
Second test
↓
Second failure
↓
...

The history contains useful information, but it is now carrying both conversation context and application state. Over time, this history becomes a full record of everything the agent has seen, done, and decided, which can be helpful for debugging or replaying execution, but it is not always the right structure for runtime decision-making.

As the sequence grows, the model is forced to retrieve relevant signals from a long stream of mixed information. Important details can become harder to surface, especially in longer-running workflows where earlier steps are far back in the context window. This is where issues like “lost in the middle” can appear, where critical information exists in the history but is not reliably attended to by the model. In other cases, the agent may simply run out of usable context entirely, leading to “out of context” failures where the necessary state is no longer visible.

That can become expensive and awkward to manage. This is where explicit state management becomes useful.

Stage 3: Explicit State Management

Instead of letting state be implicitly reconstructed from an ever-growing sequence of messages (which quickly becomes fragile and expensive as workflows grow), we explicitly define the information the workflow actually needs to carry forward. This makes execution easier to reason about and gives each step a clear contract for what it can read and update.

In practice, this means introducing a structured state object that contains only the fields required for the workflow to continue.

from typing import TypedDict


class AgentState(TypedDict):
    code: str
    tests_passed: bool
    error_feedback: str | None
    retries: int

The operations can now work against that state:

def generate_code(state: AgentState) -> dict:
    if state["error_feedback"]:
        code = repair_code(
            state["code"],
            state["error_feedback"],
        )
    else:
        code = generate_initial_code()

    return {"code": code}


def evaluate_code(state: AgentState) -> dict:
    result = run_tests(state["code"])

    if result.passed:
        return {
            "tests_passed": True,
            "error_feedback": None,
        }

    return {
        "tests_passed": False,
        "error_feedback": result.error,
        "retries": state["retries"] + 1,
    }

The execution now has a clearer shape:

A graph framework such as LangGraph provides abstractions for defining and running workflows organized around this kind of state. Instead of manually writing a while loop that controls every step, you describe the workflow as a set of nodes (the operations) and edges (the transitions between them). The framework then handles moving the state through those nodes, applying each function, and deciding what comes next based on routing logic you define.

The framework does not change what generate_code() or run_tests() actually do. Those remain application functions. What it adds is a structured way to separate what happens (the functions) from how execution flows between them (the graph). It also makes it easier to introduce things like branching, retries, and checkpoints without embedding all of that logic directly inside a single loop.

So, instead of having the main loop contain every operation and every routing decision, the application can represent those pieces separately.

A simplified implementation might look like:

from typing import Literal, TypedDict

from langgraph.graph import END, START, StateGraph


class AgentState(TypedDict):
    code: str
    tests_passed: bool
    error_feedback: str | None
    retries: int


def generate_code(state: AgentState) -> dict:
    if state["error_feedback"]:
        code = repair_code(
            state["code"],
            state["error_feedback"],
        )
    else:
        code = generate_initial_code()

    return {"code": code}


def evaluate_code(state: AgentState) -> dict:
    result = run_tests(state["code"])

    if result.passed:
        return {
            "tests_passed": True,
            "error_feedback": None,
        }

    return {
        "tests_passed": False,
        "error_feedback": result.error,
        "retries": state["retries"] + 1,
    }


def route_after_test(
    state: AgentState,
) -> Literal["generate_code", "human_review", END]:

    if state["tests_passed"]:
        return END

    if state["retries"] >= 3:
        return "human_review"

    return "generate_code"


def human_review(state: AgentState) -> dict:
    request_human_review(state)
    return {}

The important separation is now visible:

State
  ↓
Operation
  ↓
Updated state
  ↓
Routing decision
  ↓
Next operation

That structure becomes useful when the workflow needs more than a few local variables and conditions.

Comparing the Three Approaches

State Local variables Primarily message history Explicit schema
Control decisions Application code Model plus application code Explicit workflow logic
Predictability High Lower for model-driven decisions Higher for application routing
Context growth Developer controlled Can grow rapidly State can be separated from model context
Persistence Manual Depends on implementation Framework capability where supported
Resumption Manual Depends on implementation Framework capability where supported
Initial complexity Low Low to moderate Higher

The third approach adds structure, but a small workflow may not need it.

A small workflow can remain a small Python program, and in many cases that is exactly the right choice. If the logic is easy to follow, the state is minimal, and the execution path is obvious, adding a graph abstraction only introduces unnecessary structure.

The graph becomes useful when the workflow starts to grow in ways that make a single loop harder to reason about. In particular, when state needs to be tracked more explicitly across multiple steps, or when the execution flow branches into different paths that depend on intermediate results, the simple loop starts to feel overloaded. At that point, separating what the system knows (state) from what the system does next (execution flow) becomes valuable, and that is where graph-based approaches begin to make sense.

Let’s take a closer look at this distinction.

When the Simple Loop Stops Being Simple

A loop does not stop working at some fixed level of complexity. You can keep adding steps, conditions, and tool calls, and the program will still run.

The issue is not correctness, but clarity. As more behavior gets layered into the loop, it becomes harder to see what the system is actually doing at any given moment, and harder to reason about how one step affects the next.

For instance, you can start with a simple workflow:

generate → test → repair → test

At this stage, everything is easy to follow because the entire process fits in your head at once. But real agent systems rarely stay this small. As soon as you move beyond this, you begin adding practical requirements that are not part of the core loop itself, but are necessary for it to work reliably in production. These requirements can include:

  • retry limits
  • error handling
  • tool calls
  • message history
  • persistent state
  • human approval
  • resume after failure

Each of these concerns is reasonable on its own. Retry limits prevent infinite loops. Error handling makes failures observable. Tool calls extend capability. Human approval adds safety, while resume support makes long-running workflows practical.

The problem is that the loop is now responsible for all of them at once.

It is no longer just describing what happens next, but also how long to keep going, what information to remember, and when to stop or pause. Over time, the control flow becomes a mixture of execution logic and state tracking, and those two concerns start to blur together.

This is where the next step becomes important. Once the loop is carrying this much implicit information, you need a clearer way to represent what the system knows at any point in time. That is where state comes in, and why separating state from execution is the natural next step in making the system easier to reason about.

State and Execution Start to Diverge

A small agent might only need to track a few pieces of information while it runs:

  • code
  • error
  • retries

At this scale, it is still easy to treat these as local variables inside a loop. The execution logic and the data it operates on live in the same place, and you can mentally follow the program step by step.

As the workflow grows, the set of things you need to remember grows with it:

  • code
  • test_result
  • error
  • retry_count
  • messages
  • tool_results
  • security_status
  • approval_status
  • execution_id

At this point, these values are no longer just temporary inputs to a single function or loop iteration. They become persistent state that must survive across multiple steps of execution, interruptions, retries, or even process restarts.

This is where the separation starts to matter:

  • Execution is what the system is doing right now (generate, test, repair, route).
  • State is what the system must remember in order to continue correctly later.

When those two are mixed together in a single loop with local variables or message history, the program becomes harder to reason about. You start needing to reconstruct “what happened so far” from execution traces instead of simply reading a structured state object.

Passing these values manually between operations in a growing workflow becomes cumbersome not just because there are more of them, but because they are serving different roles: some are inputs to the model, some are outputs from tools, and some exist purely to control the flow of execution. Once that distinction becomes clear, the motivation for explicit state management and graph-style execution starts to make sense.

Consider the following state object that you can use to make sure the values persist as the agent moves through various states:

class AgentState(TypedDict):
    code: str
    test_result: str | None
    error: str | None
    retry_count: int
    approval_required: bool

The schema also makes a design question visible: which information actually belongs in the workflow state?

That question is easy to miss when everything is stored in local variables or appended to a message list.

Control Logic Spreads

A small workflow may have one decision:

if tests_passed:
    finish()
else:
    repair()

However, a larger workflow can end up with several:

if tests_passed:
    finish()
elif retry_limit_reached:
    request_review()
elif security_check_failed:
    run_security_repair()
elif documentation_required:
    search_documentation()
else:
    retry()

The code is valid. The execution path is simply harder to inspect.

This is the second practical benefit of graph-based design: it lets you move this growing decision logic out of a single loop and into explicit routing steps. Instead of stacking more conditions into one block, each decision becomes a separate, named transition in the workflow. The loop stays focused on execution, while routing logic becomes its own layer.

When computation and routing are mixed together, changing one part of the workflow can require reading through several unrelated conditions.

Separating the operations from the decisions about when to run them gives the workflow a clearer structure.

Retry Logic Becomes Part of the Design

A single retry is easy:

for attempt in range(3):
    result = call_model()

    if result.success:
        break

Real workflows often need different policies.

For instance, a model API failure may be retried because it is transient. A failed security check may require a different repair path. Three unsuccessful code repairs may require human review instead of another attempt.

These workflow decisions should be visible rather than buried inside a large loop.

When retry logic is hidden inside the same control flow as execution, it becomes harder to reason about what is actually being retried and why. It also makes failure handling more fragile, because exceptions and edge cases tend to get absorbed into generic loop logic instead of being handled at the point where they occur. In practice, this leads to unclear error propagation, where a failure in one step surfaces much later without context about which operation caused it.

This is why exception handling and clear error messages matter. When something goes wrong, developers need to know not just that a failure happened, but where it happened and what state the system was in at that moment. A well-structured workflow should surface errors with enough context to answer questions like: which step failed, what inputs were being processed, and what decision led to that step being executed. Without this clarity, debugging turns into reconstructing the execution path from scattered logs inside a monolithic loop.

Message History Can Become Context Bloat

ReAct-style systems make this problem particularly obvious.

If every model response, tool call, tool result, test failure, and repair attempt is appended to the conversation, the context grows with each iteration. Over time, the loop accumulates a full execution trace inside the prompt rather than outside it.

In long-running runs, this leads to context bloat, where the model is forced to process an increasingly large history that includes both relevant signals (like the latest error) and irrelevant or redundant past steps. This has direct operational impact:

  • token usage increases linearly with each iteration,
  • latency increases because each request processes a larger prompt,
  • API cost increases proportionally to context size,
  • and model performance can degrade because important signals are diluted in a long history of intermediate steps.

The solution is not automatically a graph.

First separate the two questions:

  1. What information does the model need to see?
  2. What information does the application need to remember?

Those answers may overlap, but they do not have to be identical. This separation is what prevents context bloat in ReAct-style systems, where every tool call, observation, and intermediate reasoning step can otherwise accumulate into an ever-growing message history. In a poorly managed loop, the model is repeatedly fed unnecessary past interactions, increasing cost, latency, and confusion.

A well-structured ReAct loop keeps this under control by being strict about what enters the model context at each iteration. The model should only receive the minimal working set: the current task, the latest observation, and any essential state summary. Everything else should be stored in application state outside the prompt.

Structurally, the loop should look like this:

  1. Build a compact context from state (not full history)
  2. Ask the model for the next action
  3. Execute the tool or operation
  4. Update external state with the result
  5. Repeat with a refreshed, minimal context

By continuously reconstructing a clean prompt from state rather than appending raw history, the system avoids context bloat while still preserving full execution memory outside the model.

Human Intervention Creates Another Boundary

Some workflows need a person to approve an operation before execution continues, and this becomes especially important when you run real-world autonomous systems that operate over real data, real infrastructure, and real risk.

For our coding agent, Human-in-the-Loop (HITL) is a dedicated step of the loop:

modify source
    ↓
run tests
    ↓
request approval
    ↓
push change

In a local script, this is just another conditional branch. But in a production autonomous agent, the “request approval” step is not instantaneous. It may depend on a human reviewing a diff, a security engineer validating a change, or an external system enforcing compliance. That means the human review and approval can take minutes, hours, or even days.

This is where HITL systems introduce a fundamental requirement: the agent must be able to pause execution without losing its internal progress or reasoning context.

A production workflow therefore needs to preserve information such as:

  • current state
  • approval status
  • execution ID
  • pending operation

The process can then pause:

agent reaches approval point
        ↓
state is saved
        ↓
execution pauses
        ↓
human reviews change
        ↓
approval is recorded
        ↓
execution resumes

A graph framework can provide mechanisms for this type of interruption and resumption. The underlying requirement is ordinary workflow management: preserve enough state to know where execution stopped and what should happen next.

When Should You Use a Graph?

The simplest implementation should usually be the first one you try, because most agent workflows do not need anything more complex at the beginning. A normal loop is often enough to express the full execution flow clearly, especially when the number of steps is small and the state is easy to track.

A normal loop is a good fit when:

  • the workflow has only a few steps,
  • state is small,
  • execution is short-lived,
  • control flow is easy to follow,
  • persistence is unnecessary,
  • and failure handling is straightforward.

For example:

for attempt in range(3):
    result = run_tests(code)

    if result.passed:
        return code

    code = repair_code(
        code,
        result.error,
    )

raise RuntimeError(
    "Unable to produce working code"
)

There is little reason to introduce a workflow framework for this alone.

Explicit state management becomes useful when several operations share substantial state or when message history is carrying information that would be easier to represent as structured application data. A graph framework becomes more useful when the workflow is long-running, needs durable checkpoints, must pause for human input, or has enough execution logic that tracing the control flow through a single loop is becoming difficult.

Use the framework abstraction because of those requirements. Do not use it simply because an LLM is involved.

In practice, this comes down to how much coordination your workflow needs between steps. In a small loop, you can keep everything in local variables and reason about the flow directly. But as soon as multiple steps need to read and update the same information, that approach starts to break down.

State management solves this by making the “memory” of the system explicit. Instead of relying on scattered variables or reconstructing context from a growing message history, you define a structured object that represents everything the workflow needs to know at any point in time. This makes it easier to inspect, debug, and extend the system because the current situation is always visible in one place.

It also becomes especially useful in scenarios where execution is not linear or short-lived. For example, if a workflow needs to pause for human approval, resume after a failure, or continue processing after a system restart, the state becomes the single source of truth that allows the system to pick up exactly where it left off. Without this, you end up trying to reconstruct intent from logs or conversation history, which quickly becomes unreliable as complexity grows.

This is why state management is not just an implementation detail in graph-based systems. It is the foundation that allows workflows to move beyond simple loops into something that can be paused, resumed, inspected, and reliably extended over time.

Key Takeaways for Building Reliable LLM Workflows

Before reaching for a graph framework, identify the actual execution problem.

Ask:

  1. What information must survive from one step to the next?
  2. Which of that information belongs in model context?
  3. What operation should run next?
  4. What conditions cause the workflow to stop, retry, or escalate?
  5. What happens to the state if the process fails halfway through?

For a small agent, ordinary Python may answer all five questions clearly.

As the workflow grows, explicit state management can make those answers easier to represent and test. A graph framework adds another layer when the workflow also needs durable execution, interruption, resumption, or more structured orchestration.
