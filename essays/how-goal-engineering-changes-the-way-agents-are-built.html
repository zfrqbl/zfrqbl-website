How Goal Engineering Changes the Way Agents Are Built

On November 14, 2026, LangChain published a post titled "Goal Engineering: How to Design Goals", written by Harrison Chase with Mihir Garimella and Anshul Gupta of Actively AI. It closes with a line that sounds like marketing: "Prompt engineering and context engineering will disappear, but goal engineering will remain." The reasoning behind that line is more interesting than the line itself, and it marks a real change in how agents get built.

The timing is telling. The day before, LangChain announced a $300 million Series C at a $3 billion valuation, and the post says more than 7,000 organizations already rely on its LangSmith platform, with Workday cutting agent deployment time from five months to under a day (Series C announcement). The blog agenda is never neutral. But the goal engineering argument stands on its own, and the people making it are also shipping it in code.

The trajectory

Chase describes the path in one paragraph: "The scope of tasks that agents can take on has increased drastically over the past few years. They have gone from simple text generation to tool calling and decision making to executing full tasks. The future of agents is them taking on open ended goals and driving towards completion of those goals" (Goal Engineering).

His example of that future is Hone. Hone raised a $60 million seed round from Benchmark and Index Ventures (Introducing Engines), and its framing is blunt: "An Engine meets goals rather than completing tasks." You assign an engine an outcome like "improve customer retention", it onboards itself, and it owns that outcome. Chase notes that a key part of Hone's setup is defining metrics for the agent to optimize.

That is the shift. Step by step instructions tell the agent what to do. A goal tells it what to achieve and leaves the how open. The design problem moves from prompting to scoping: what is the goal, what does done look like, and how does the agent stay pointed at the right thing? LangChain calls that goal engineering.

The core argument is feedback

The main claim is about feedback, not about benchmarks. From the post: "you want to design the scope of an agent such that it makes it as easy as possible to give feedback as the agent operates within that scope."

The reasoning runs like this. When agents mess up, a big reason is lack of the right context. Some context is easy to supply, like access to documents, APIs, or databases. The trickiest context is what is not written down anywhere. Taste, judgment, risk tolerance. That context can only reach the agent through feedback from a human expert.

The post's example is marketing. An agent that optimizes ads to improve marketing performance needs more than factual context. It needs taste: what sounds and looks good, how provocative the brand can be. An agent that cannot absorb feedback on those things quickly becomes useless.

This reframes where agent performance stalls. "The bottleneck for agents performing is often them learning from feedback." A surprising piece of guidance follows. Invest in an intuitive, delightful UX for reviewing agent work. The review interface becomes a production constraint, not a demo nicety.

Goals are already in the tooling

The most concrete form of goal engineering in LangChain's stack is in Deep Agents Code, its terminal coding agent (Goals and rubrics docs). The docs define a goal like this: use it "when you have one measurable objective and want Deep Agents Code to draft acceptance criteria before it starts."

The workflow is interactive.

/goal add OAuth refresh handling

Deep Agents Code drafts acceptance criteria and opens them for review. Once accepted, the goal stays active across turns until it is paused, completed, blocked, or cleared. You can amend it mid-work without restarting, pause and resume it, and inspect it. The command set covers the whole lifecycle: /goal add, /goal amend, /goal pause, /goal resume, /goal show, /goal clear, /goal model, and /goal max-iterations. Each follow-up turn is graded against the goal's acceptance criteria until the work is done.

A longer session shows the pattern. You steer by goal, not by re-explaining.

/goal migrate auth callbacks to the new API
start with the OAuth callback
now update the tests
check the docs too

Rubrics are the other half. A rubric is for when you already know the criteria: /rubric set "tests pass; no unrelated files changed; help text is updated". It can apply to the next turn only or persist until cleared. Non interactive runs use flags: dcode -n "implement OAuth refresh handling" --rubric "tests pass; no unrelated files changed" --rubric-max-iterations 3.

Two mechanisms matter here. The agent drafts its own definition of done, and a human approves it before work starts. And the criteria survive across turns, which is what makes long horizon work possible: the goal, not the accumulating chat instructions, grades each step.

The loop pattern is older

The other piece of the pattern is the planner loop, and LangGraph shipped it back in February 2024 (Plan and Execute Agents). Plan and execute agents split work into a planner that produces a multi step plan, executors that run each step, and a replan step after execution. The design draws on Plan and Solve Prompting and on Yohei Nakajima's BabyAGI.

The motivation was practical. ReAct style agents call the LLM once per tool invocation and plan one step ahead. A planner forces the model to think through the whole task first, which the LangChain team says improves task completion rates. It also cuts cost, because individual steps can run on smaller, domain specific models. LLMCompiler, the third architecture in that release, streams a DAG of tasks and the paper claims a 3.6x speedup from scheduling tasks as soon as their dependencies are met.

The goal loop is the same shape with one addition: a definition of done. Objective in, plan out, execute, observe, replan, repeat until the criteria are met. In LangGraph that looks like this, following the documented plan and execute example with a criteria check:

from typing import Annotated, TypedDict
import operator
from langgraph.graph import StateGraph, END

class GoalState(TypedDict):
    objective: str                               # the goal, not the steps
    criteria: list[str]                          # acceptance criteria
    plan: list[str]                              # current plan
    completed: Annotated[list[str], operator.add]

def planner(state: GoalState) -> dict:
    return {"plan": plan_for(state["objective"], state["criteria"])}

def executor(state: GoalState) -> dict:
    step = next_step(state["plan"], state["completed"])
    return {"completed": [step], "result": run(step)}

def replanner(state: GoalState) -> dict:
    if criteria_met(state["objective"], state["criteria"], state):
        return {"plan": []}
    return {"plan": plan_for(state["objective"], state["criteria"], state["completed"])}

workflow = StateGraph(GoalState)
workflow.add_node("planner", planner)
workflow.add_node("executor", executor)
workflow.add_node("replanner", replanner)
workflow.set_entry_point("planner")
workflow.add_edge("planner", "executor")
workflow.add_edge("executor", "replanner")
workflow.add_conditional_edges(
    "replanner",
    lambda s: "planner" if s["plan"] else "end",
    {"planner": "planner", "end": END},
)

The functions plan_for, next_step, run, and criteria_met are illustrative stand-ins. The graph structure is the point: the goal and its criteria live in state, the planner re-derives steps from them, and the loop ends only when the criteria pass.

The case study that makes it concrete

Actively AI builds agents for sales teams. Its first goal-oriented design ran one agent per account. Each prospective customer got an agent tasked with moving that account forward, producing actions for sales reps to approve. It seemed natural. The account is the context.

It failed in a specific way. Progressing one account involves many different jobs spread out over time, so at any moment there were only a few things to review per agent, and salespeople switched constantly between agents. The most valuable knowledge, how to outbound, how to reply, how to strategize a deal, how aggressive to be, was spread across every account agent. Feedback learned on one account had no path to the others, even when the lesson applied to all of them.

The rewrite changed the unit of work. Actively built agents called motions, on top of LangChain's Deep Agents. A motion is a job: outbounding, early stage deal progression. A motion covers a batch of similar tasks, so a salesperson reviews them together, and feedback on one task transfers to the whole motion. Account context, which is mostly objective and already written down, is assembled by background context gathering agents. The work agents own the slice of the sales motion and pull in account context as needed.

That is the pattern in miniature. The account looked like the right boundary. The motion was the right boundary, because it made review cheap and feedback reusable.

The half that is still unsolved

Two weeks earlier, on November 2, 2026, Chase published a companion post (New context engineering challenges in late 2026), and it is more honest about open problems. Goal tracking is hard: getting agents to try new experiments in pursuit of a goal instead of repeating what worked, getting them to think about broad goals instead of small tasks, keeping them consistent over long time horizons.

Then there is alignment. "Goal design is hard by itself. It will be very hard for users to design goals that agents can not cheat." The example is the classic one. Tell an agent to get rid of all bugs in a codebase, and it may delete the codebase, because no code means no bugs. The post links to DeepMind's writeup of specification gaming (Specification gaming). The open question is how to build a harness that keeps an agent focused on a goal without letting it over optimize.

Chase is explicit that nobody has general solutions yet. That honesty matters. Teams adopting goal style agents are adopting a design with unsolved corners.

What the threshold claim actually means

Why would goals beat step by step instructions in general? The meta argument across the two posts is this. Instructions encode how someone once thought the work should be done. They go stale, and correcting them means editing the instruction, which is slow and keeps the agent dependent on the instruction giver.

A goal plus a review loop encodes only the outcome and the corrections. The feedback channel keeps working as the world changes. Knowledge gets extracted from the human expert and stays in the loop, not in a prompt. That is the sense in which goal engineering remains: the feedback loop is the part that keeps functioning.

The claim that prompt engineering and context engineering will disappear is the promotional half. Prompting and context still decide whether the agent can even attempt the goal; the November posts themselves are full of context engineering concerns, from memory to browser use to async subagents. What is changing is the center of gravity, from writing instructions to designing goals and their review loops.

What builders should take from this

The practical thesis has four parts.

Scope agents around review, not around task boundaries. If a human can review a batch of work in one place, feedback compounds. If their attention is scattered across many agents, feedback does not travel.

Make done explicit before the work starts. A goal where the agent drafts acceptance criteria and a human approves them is a cheap alignment check before tokens get spent. Chase names the cost of pointing agents wrong: wasted tokens.

Build the review interface seriously. If the bottleneck is learning from feedback, the feedback UX is a production constraint, and LangChain says to invest in it.

Assume the goal will be gamed. Metrics are proxies, and proxies get overfit. The harness question is not whether the agent will cheat, but how you will detect it.

The position

The shift is real, and it runs deeper than a blog catchphrase. The unit of design moves from the instruction to the loop: goal, plan, execute, review, learn. Step by step instructions made the agent an executor of captured process. Goals plus feedback make it a worker that gets corrected into alignment, the way a new hire does. That changes the job of the agent builder. The job is no longer writing better prompts. It is designing goals a human can review and a machine can be held to.

Whether prompt engineering truly disappears is the wrong question. The right question is which loop wins in production: writing better instructions, or giving better feedback. Everything in the November posts points to the feedback loop.
