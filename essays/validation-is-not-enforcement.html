Validation Is Not Enforcement: Your Schema Already Has the Logic Your Tool-Calling Agent Needs

Your agent drafts a plan: roll out auth-api to production, run a smoke test, update the incident channel. It calls the tool `deploy_service` with `{"service": "auth-api", "version": "2.1.0", "environment": "production"}`.

The tool rejects it. Production deploys also require an approval ticket, a rollback version, and a health check endpoint. The agent retries, adds the ticket, and the tool rejects it again: the rollback version is still missing. Third call, it adds that too. One deployment step has now cost the loop three API calls, a pile of recovery tokens, and a plan that had to be reworked around a blocked step.

None of this had to happen. The business rules the agent tripped over were expressible in JSON Schema all along, in the agent's own tool definition. The failure is not the model's fault and it is not the schema's fault. It is the gap between validating output and enforcing it, and the industry quietly ships that gap in the most expensive layer of every agent stack.

JSON that parses is not JSON that passes. Validation is not enforcement. I want to argue that the conditional subset of JSON Schema, enforced at generation time, is the contract your tool-calling agent was missing. Bolting rules on after generation is rejection sampling with extra steps. And the schema you already wrote is the cheapest logic you will ever get.

JSON that parses is not enough

Parsing guarantees shape. It does not guarantee contract. When an agent's tool arguments arrive, they are either valid against the tool's schema or the step fails. In agentic workflows a failed step does not just return an error, it spends tokens on recovery: retry the call, re-read the plan, sometimes re-plan the whole sequence. Latency and spend pile up exactly where the failure was avoidable.

The rules agents actually trip over are conditional. If `environment` is `"production"`, require `approval_ticket`, `rollback_version`, and `health_check_endpoint`. If `sort_by` is present, require `sort_order`. If `page_token` is present, require `page_size`. These are not exotic constraints. They are the everyday shape of tool contracts: fields that are individually optional but meaningful only in combination.

JSON Schema expresses all of this natively. `if/then/else` handles the value-based case, one schema branch for dev deploys, another for production. `dependentRequired` handles the presence-based case, `sort_by` demands `sort_order`, `page_token` demands `page_size`. The keywords are standard and documented. The problem is not the vocabulary. The problem is that many inference providers' structured output implementations enforce only the easy subset (types, required, enums) and silently ignore the conditional keywords. No error, no warning, just output that passes a shape check and violates the contract underneath.

What your schema already says

Here is the deployment tool as a schema, with the conditional branch spelled out:

{
  "type": "object",
  "properties": {
    "service": { "type": "string" },
    "version": { "type": "string" },
    "environment": { "enum": ["dev", "staging", "production"] },
    "approval_ticket": { "type": "string", "pattern": "^PROD-[0-9]{4}$" },
    "rollback_version": { "type": "string" },
    "health_check_endpoint": { "type": "string" }
  },
  "required": ["service", "version", "environment"],
  "if": { "properties": { "environment": { "const": "production" } } },
  "then": {
    "required": ["approval_ticket", "rollback_version", "health_check_endpoint"]
  }
}

One tool definition, two different sets of requirements. A dev deploy needs three fields; a production deploy needs six. The `then` branch is the business rule, sitting where the agent can see it.

The search API variant uses the other keyword:

{
  "type": "object",
  "properties": {
    "query": { "type": "string" },
    "sort_by": { "type": "string" },
    "sort_order": { "type": "string" },
    "page_token": { "type": "string" },
    "page_size": { "type": "integer" }
  },
  "required": ["query"],
  "dependentRequired": {
    "sort_by": ["sort_order"],
    "page_token": ["page_size"]
  }
}

`sort_by` without `sort_order` is a malformed request, and the schema says so before any model output is sampled.

The four workarounds and what they cost

Teams that cannot rely on the schema as a contract do not give up. They bolt guardrails onto the agent loop at runtime, and each workaround moves complexity into the most expensive layer of the system.

**Make everything optional and validate after.** Flatten the schema, mark every conditionally required field optional, let the model generate, then validate in application code. When validation fails, and it will, especially with two or three interacting conditions, retry. Each retry is another API call, more latency, more tokens, more money. You have turned schema logic into a rejection sampling loop, and rejection sampling is how you pay for the same answer three times.

**Split one tool into many.** Instead of one deployment tool with conditional branches, define `deploy_to_dev`, `deploy_to_staging`, and `deploy_to_production` as separate tools. Schema complexity drops, and the agent's action space grows. Now the model must choose the right tool before it makes any call. The prompt footprint grows with every extra entry, and tool selection becomes another probabilistic decision layered on top of the one you were trying to de-risk.

**Push the rules into application code.** Accept flat output and enforce conditions in your service layer. Now the schema says one thing and the code says another. Business rules change, someone edits the schema, someone else patches the validator, and the two drift until a production deploy slips through with the wrong ticket format. Schema and code drift is how contracts rot silently.

**Encode the constraints in the prompt.** Add instructions like "if the environment is production, include an approval_ticket matching PROD-XXXX." This is probabilistic and brittle, and its failure mode is the worst one: silent. The model produces output that looks valid but violates a constraint it forgot mid-generation. Prompt glue turns a structural guarantee into a memory test.

All four are different ways of saying the same thing: the agent cannot rely on the schema as a contract. And all four are unnecessary, because the alternative exists.

Enforcement beats validation in the loop

Validation after generation tells you what went wrong. Enforcement during generation prevents the wrong branch from being produced in the first place. In an agent loop that difference compounds: steps do not fail, so the agent spends its tokens progressing instead of recovering, and the tool never has to reject a call that should never have been made.

The hard part, the part most libraries get quietly wrong, is enforcement itself. Structured generation looks easy in a demo and is a compiler problem in production. Most structured generation libraries accept a JSON schema, translate it to a grammar with string manipulation, and silently ignore whatever the translation dropped. The dottxt team calls this silent constraint violation, and they have documented how common it is. A schema that constrains a date field with `pattern: "^2026"` should only produce dates in 2026. Their testing found engines such as XGrammar, the default in many inference servers, silently ignore the pattern and allow any date. No error. No warning. Just wrong output that passes validation.

The same team's feature comparison quantifies the gap. Against the JSON Schema feature set, their dotjson engine supports 43 features natively, lists 14 as unsupported, and has one unsound case. XGrammar supports 28, leaves 19 unsupported, and is unsound on 12. Unsound is the dangerous column: a feature that compiles but behaves incorrectly. Twelve features in the default engine of many inference servers that produce output which looks schema-valid and is not. If the whole point of structured generation is enforceable guarantees, a library that drops constraints defeats the purpose, and a library that is silently unsound on a dozen features is worse than no library at all.

This is why the fix has to live in the engine, not the prompt or the validator. Treat schema translation as a compiler: lower the constraints through intermediate representations toward a grammar, validate that each constraint is realizable, and either support the feature correctly or refuse it loudly. The property you want from a structured generation engine is not "supports my schema." It is "fails visibly when it cannot support my schema."

The enterprise precedent: XSD 1.1 and FHIR

None of this is new. Enterprises spent two decades learning that business rules belong in schemas, and the lessons are already written down.

XML Schema 1.1, a W3C recommendation since 2012, added assertions that let a schema express co-occurrence constraints across elements. Before that, the only way to say "if this element is present with that value, these other elements become required" was validation code outside the schema. The same drift problem teams are rediscovering with tool-calling agents. XSD 1.1 made the constraint declarative and enforceable at validation time, in the schema, where the contract lives.

FHIR, the healthcare interoperability standard, went further: every resource definition carries invariants, machine-checkable expressions attached directly to the schema. A Patient record must satisfy constraints on its own fields, and a resource that violates an invariant is not a resource. It is an error that other systems refuse. Healthcare put business rules in the schema because lives depend on the contract holding.

The tool-calling agent is the same problem one generation later. The pattern was settled twice before: put the rule in the schema, enforce it at the boundary, and the systems around you stay dependable. What changed is that enforcement can now move earlier, from validation time to generation time, so the boundary never sees an invalid call at all.

One schema as the shared contract

The useful consequence of all this is that you need exactly one artifact. The same JSON Schema that defines your Pydantic model, the same one that appears in your OpenAPI spec, the same one your agent's tool definition carries, can be the sole source of truth. The conditional keywords work identically in every slot. The Pydantic model validates the same rules your tool-calling agent is forced to generate against, and the OpenAPI spec documents the same contract the operator reads.

One schema, three consumers, zero drift. When the business rule changes, say production deploys now require a change request in addition to the ticket, you edit the schema once. The model, the validator, and the documentation all move together. That is the difference between a schema as a shape checker and a schema as a contract.

What enforcement cannot do

A constraint is a floor, not a guarantee of truth. Enforcing the `then` branch makes the agent emit an `approval_ticket`; it does not make the ticket real. The model can generate `PROD-9999` against a pattern that matches and still hand you a ticket that does not exist in the tracking system. Schema enforcement eliminates structural failures. Semantic failures survive it completely.

And enforcement is only as good as the engine. The feature tables above are the cautionary tale: an engine that is unsound on a dozen features will happily enforce the easy subset and ignore the branch your production rules live in. Before you trust an engine with a conditional schema, check the table. Prefer engines whose failure mode is a loud refusal over a silent violation.

The honest summary is one sentence: structure is a contract you can enforce, content is a judgment you still have to verify, and the two are not the same problem.

The verdict

The deploy that needed three tries needed one. The agent's first call could have carried the service, the version, the environment, the ticket, the rollback version, and the health check endpoint, all because the schema said production deploys require them and the generation engine refused to produce anything else.

The retries, the tool explosion, the drift, the prompt glue: they all exist because validation was mistaken for enforcement. JSON Schema already expresses the rules. The engines now exist to enforce them. And the agent that treats its schema as a contract, enforced at generation time, spends its tokens doing work instead of recovering from work it should never have attempted. That is the difference between an agent that has guardrails and an agent that has a contract. The contract is cheaper.
