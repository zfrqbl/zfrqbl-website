Context Engineering with Deep Agents

# Context Engineering with Deep Agents

Your support agent carries a vector database full of "memory" and still asks for an order number it was given three weeks ago. The deploy assistant repeats the cache mistake it made in March. The team's answer in both cases is the same: add memory, which in practice means embedding everything into a vector database, wiring in a retriever, and calling it done.

The reflex is wrong in a specific, expensive way. A vector database is a retrieval component. It stores chunks, finds near matches, and hands them back. Memory, as the people who build and study agents use the word, is a family of at least eight distinct problems, and retrieval solves one of them. Treat the database as the whole system and you pay for storage and indexing while the behavior you wanted, an agent that stops repeating itself, never arrives. The agent still forgets. It just forgets with a latency budget and a monthly bill.

Memory is eight different problems

The taxonomy is not new. CoALA, the Cognitive Architectures for Language Agents paper from 2023, formalized four types: working, episodic, semantic, procedural. The practitioner literature has since expanded the list. Neo Kim's widely copied formulation and the articles built on it add retrieval, parametric, and prospective memory. Production memory systems tack on an eighth, meta-memory, which is how a team turns raw logs into lessons. Eight types, and each fails in its own way:

  1. Working memory. What is in front of the model right now: system prompt, recent turns, tool outputs. Bounded by the context window, gone when the session ends, and every token in it costs money on every call. This is the only type the model sees directly.
  2. Episodic memory. Records of specific events with outcomes. "On 12 March the deploy raised latency after a cache change." Timestamped, searched by similarity and filtered by time, pruned as it ages. The agent's diary of past runs.
  3. Semantic memory. Facts not tied to one event: "this user works in fintech and prefers concise answers." Lives in a profile, a knowledge graph, or a structured store consulted in any future session.
  4. Procedural memory. How to do things: "run the tests before you suggest a deploy." Rules, workflows, tool patterns, stored in prompts, skill files, config, or code, only rarely in an embedding.
  5. Retrieval memory. Pulling relevant material from a corpus at run time. Documents, tickets, code. This is the vector database slot.
  6. Parametric memory. Knowledge baked into the weights during pretraining or fine-tuning: language, reasoning patterns, world knowledge. The model carries it everywhere and cannot set it aside.
  7. Prospective memory. Future intentions: scheduled goals, reminders, the steps a long-horizon task still needs. A task queue or scheduler, not a similarity search.
  8. Meta-memory. Memory about memory: summaries, reflections, evaluations. "That strategy worked well for onboarding," "do not use Tool A for payments anymore." It compresses bulky episodic logs into durable lessons.

Three of the eight describe what is remembered: episodic, semantic, procedural. Two describe where knowledge lives and how it gets back to the model: retrieval, parametric. The guides are explicit about the consequence: mixing the what axis with the where axis is why "just add a vector DB" feels like an answer and then quietly fails.

Retrieval is one of the eight

Watch what a vector database actually does. It embeds text, indexes it, and returns nearest neighbors: half of retrieval memory, and retrieval memory is one of eight. It does not decide what is worth storing. It does not extract facts into a semantic profile, so the "prefers concise answers" fact never gets written. It does not encode a workflow, schedule a reminder, or summarize logs into a lesson. It does not even decide when its results enter working memory; something else must notice a retrieved chunk is relevant and place it in the window. Useful memory has a write path and a read path. The database is only the middle of the read path, and even there the neighbor list is only as good as the timestamps and filters around it when the question is "what did we try last time." The store is a filing cabinet, the least interesting part of a memory system.

Context rot: what happens when the window is the whole brain

The reason teams reach for memory at all is that agents degrade as they work. Every long-running agent accumulates instructions, tool results, files, and drafts. The more history, noise, and tool output a model carries, the worse its accuracy and reasoning tend to get. LangChain calls this context rot. The opening example in Jess Weng's October 2026 post on context engineering with Deep Agents is a competitive analysis agent: every Monday it researches five competitors, pulls market data exports of tens of thousands of rows, searches news, takes notes, drafts a report, revises it, and formats it. By the formatting step it is dragging five raw exports, dozens of search results, and two stale drafts through every model call. Most of that context is irrelevant to the actual task.

Weng's framing is worth keeping: an agent is a model with a harness around it, and every technique in this story lives in the harness, not the model. The harness gets the model the right context at the right time. Get that discipline right and most memory problems that architecture can solve are solved.

What context engineering actually does

Five techniques move context out of the active window without deleting it.

Offloading. Large tool results and oversized user messages are written to disk before the model sees them. A tool result past roughly 20,000 tokens is saved to a file; the model gets a preview of the first and last few lines plus a path, then pages through the file when it needs a specific number. A pasted transcript over 50,000 tokens gets the same treatment. Nothing is thrown away. Truncation is lossy; offloading keeps the data recoverable.

Summarization. Context still climbs slowly, so the harness checks token usage before every model call. Past 85 percent of the window, a separate LLM call condenses the older messages into one summary. Recent messages stay verbatim, so nothing fresh gets paraphrased. The summary is written back to disk, so the agent can recover a detail from Company A's research mid-draft. It cycles: the next summary includes the previous one, a rolling digest of the run. It can also fire on a topic change instead of a token count.

Skills. Instructions for a quarterly business review do not belong in the system prompt of an agent that writes one per quarter. A skill is a folder of instructions with optional scripts and reference docs. At startup the harness scans the skills directory and reads only the header of each SKILL.md; on every model call it adds names and descriptions to the prompt. Full instructions load only when the model decides they are relevant. That progressive disclosure means ten skills cost about as much context as ten one-liners.

Subagents. Work you already know will be noisy, researching a company across dozens of searches and pages, runs in its own context window. The subagent does the noisy work and returns three bullet points; the main agent never sees the noise. Because subagent tasks are small and scoped, they can often run on a cheaper model and in parallel.

Long-term memory files. What the agent learns is saved in a plain markdown file in storage you control. It is loaded at the start of a run, injected into the system prompt on every model call, and updated when the agent learns something worth keeping, like your formatting preference. Because it is a file rather than a provider-side blob, you can point the same backend at a different model and the memory survives the switch.

Each technique is middleware, code plugged into points in the agent loop: before the agent starts, around each model call, around each tool call. At each point it reads the context and changes it before the next step runs. The harness owns the context window and spends it deliberately. Retrieval pulls in only what the agent needs, but the article is explicit that retrieval solves half the problem: even a precise agent accumulates unnecessary messages, tool results, and intermediate work.

The taxonomy tells you which problem; the engineering fixes it

The two views fit together, and the fit is the point. The taxonomy tells you which problem you have; context engineering gives the fix. Offloading and summarization are working-memory management. Skills are procedural memory. The long-term memory file is semantic memory with an episodic update path. Subagents are working memory partitioned across processes. Retrieval is retrieval memory. Both describe the same system: one says what to remember, the other how to hold it.

The mapping is also where misdiagnosis shows up. Agent failed because the fact was never learned? A summarization threshold will not help; you need extraction and a semantic store. Failed because the window is full of noise? A bigger vector index will not help; you need compaction. Failed because there is no skill for the task? No amount of retrieval fixes that; you need a procedure. Name the failure, map it to a type, then pick the technique. Teams that skip those steps buy the most expensive store on the list and wonder why the forgetting continues.

What to do on Monday

Practical guidance, in the order it usually pays off.

First, write the failure down before buying anything. One sentence will do: "the agent re-asked for the order number it already had." That is a semantic memory gap, a fact that should have been extracted and stored, and you will not fix it by re-embedding the conversation history harder.

Second, discipline working memory before you add stores. Offload large tool results instead of truncating them. Keep compaction recoverable; summaries belong on disk, not in the void. Adjust the thresholds to fit your task, because one workload's defaults rarely fit another.

Third, move know-how into skills. Instructions that fire once a quarter should cost you nothing on the other days. Progressive disclosure is the cheapest memory optimization available.

Fourth, isolate noisy work behind subagents, and let the main agent carry conclusions rather than process.

Fifth, own the memory. Files in your storage survive a model or provider change. A memory you cannot carry across vendors is a lease, not memory.

Sixth, add types in layers as the evidence demands: semantic when the agent must remember across sessions, episodic when it must learn from failures, prospective when it plans ahead, meta-memory when the logs outgrow the lessons. Very few agents need all eight, and the ones that claim to probably cannot tell you what each layer is for.

Seventh, respect the freshness horizon. An account balance goes stale in seconds; fetch it from the system of record when it matters, do not cache it in memory where it will be confidently wrong later. A user's role changes slowly and belongs in a profile.

The store is the last decision

The vector database is a real component with a real job. It is retrieval memory, and retrieval is one of at least eight distinct problems that get the word "memory" attached to them. The agent that keeps your order number in a profile, runs the tests before it deploys, and loads the QBR format from a skill when it needs it is not doing anything exotic; it is using the right component for the right type. The store is not the system. The system is whoever decides what to keep, what to retrieve, what to summarize, and what to place in front of the model. That is context engineering, and that is where memory actually gets built.
