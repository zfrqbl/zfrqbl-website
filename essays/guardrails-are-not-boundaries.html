Guardrails Are Not Boundaries

The agent's refund tool accepts any amount up to ten thousand dollars. The policy says nothing over two hundred goes out without a second approval. The stack around the agent does everything the industry currently knows how to do: the tool call is generated against a JSON schema, Llama Guard screens the input, a moderation classifier watches the output, and a validator rejects out-of-policy calls so the loop can retry.

An email arrives mid-task, a link and a gentle nudge about a VIP customer. The agent follows it, decides the customer qualifies for a courtesy exception, and generates {"action": "refund", "amount": 499.99}. The JSON is valid against the schema. The call passes the shape check. The classifier flags it this time, so the money does not move. A detection system caught a violation the architecture was supposed to make impossible.

Every check in that stack ran after the token was sampled. That is the common shape of a guardrail, and it is why "guardrail" is the right word. A guardrail does not stop you from leaving the road; it makes the crash cheaper when you do. If the goal is an agent that cannot do the thing, the guarantee has to live where the decision is made. Constrained decoding can deliver that, but only for the subspaces the world lets you enumerate before generation starts. Everywhere else, the enforceable "cannot" is a capability question, and it belongs at the boundary around the tools, not in a classifier watching the output.

Formatting fixed integration, not behavior

The first battle was JSON compliance, and guided generation won it. The Efficient Guided Generation line of work (dottxt, arXiv 2307.09702) showed that a finite-state machine over the grammar can mask disallowed tokens at each decoding step, and engines like XGrammar (arXiv 2411.15100) made that commodity infrastructure. Structured output is now a solved integration problem, which is exactly why the industry moved on and forgot that format is the least interesting thing the output carries.

A schema-perfect payload can still be an illegal discount. The generated object can satisfy every type, every enum, every regex, and still encode a refund that violates policy, a compliance answer that is wrong for this jurisdiction, a tool call that no one authorized. The validator sees well-formed data and approves the shape. The shape was never the problem. Format governs how the agent talks to the system; it says nothing about what the system should let the agent do.

What "cannot" actually buys you

Constrained decoding works by making the wrong output unrepresentable. At each step the sampler can only pick from tokens the grammar allows, so the set of possible outputs equals the set of authorized outputs. "The model probably won't pick that token" becomes "that token does not exist." That is a genuine guarantee, declarative and exact, and it is worth a great deal where it applies.

It applies wherever the decision space is enumerable in advance. A region field constrained to IN ('East','West'), a multi-choice question, a JSON Schema, a DDL-like set of allowed rows: these are finite, knowable before decoding starts, and the masking is complete. The guarantee is only as good as the spec, and the spec is only as good as your ability to write down every legal value up front.

Where token masking runs out

An agent does not emit one constrained field. It picks a tool and fills its arguments, and the result feeds the next choice, so each step opens the space wider. Frontier models fail nested API sequences at 28% on the NESTful benchmark (arXiv 2409.03797) and below 10% on Databricks' function-calling evaluation, and the errors concentrate exactly where a grammar would have to describe the whole world, because the error an abstract API returns and the shape of a response you have not seen yet are not enumerable in advance.

What is legal next depends on what came before. A FileRef only exists after fetch_file returns it, a TestResult only exists after a run completes, so the valid space is built at runtime, one tool call at a time. No grammar written before decoding can enumerate it, because the grammar would need to know the tool's future outputs. And the actions agents take have side effects on the world, on files, on accounts, on deployed services, which cannot be masked away at the logit level. You can constrain the tokens that name a tool; you cannot constrain what the tool does to the world by constraining tokens at all.

Why guardrails are filters, not boundaries

The post-hoc stack is where most safety budgets go. NeMo Guardrails, Llama Guard, moderation classifiers: sample the output, classify it, block the bad ones, retry. This is a filter, and a filter has the two properties of a filter: it can be fooled, and it can be bypassed. OWASP ranks prompt injection as the number one generative AI risk, and the benchmarks explain why. InjecAgent (arXiv 2403.02691) showed indirect prompt injection steering GPT-4 agents into harmful actions across finance, smart-home, and email tools. ToolHijacker (arXiv 2504.19793) pushed tool-selection hijack to 96.7% on GPT-4o. ToolEmu (arXiv 2309.15817) found that even the safest LM agents fail dangerously 23.9% of the time in an emulated sandbox.

Read those numbers the way they are written: the classifier is not failing rarely, it is failing at the stakes that matter most, and the attacker is not guessing, they are aiming. A detection system can only catch what it recognizes, and the whole point of an injection attack is to produce output that looks exactly like what the system expects to see.

The control layer is a capability system

dottxt's control-layer post makes the right move: stop sampling and then validating, compile the authorization policy into the machinery so violations are unrepresentable. The direction is right, and the mechanism has a fifty-year-old name. The correct lineage is capability-based security: least privilege, confused-deputy resistance, revocation, and the design discipline of making illegal states unrepresentable. Miller, Yee, and Shapiro's Capability Myths Demolished is the intellectual spine, and the modern packaging is SELinux-style mandatory control around a probabilistic generator.

Agents make perfect confused deputies. They carry a user's authority into conversations they do not control, and an attacker who convinces the agent it is acting on the user's behalf inherits that authority wholesale. The capability answer is the same one the operating systems community settled on decades ago: authority travels per call, scoped to exactly what that call may touch, and nothing the agent says can widen the scope.

The reason capability thinking fits agents so well is that injection attacks hijack tool selection, and selection is exactly what capabilities cut off at the root. If the payment tool is simply not in the agent's capability set for this conversation, no prompt, no matter how clever, can select it, because the runtime rejects the call before any model output is involved. Detection loses because it reacts; the capability boundary fails closed by construction.

Type-safe tool graphs: the enumerable middle ground

The most useful thing in dottxt's post is the concrete suggestion hiding inside the vision: treat the tool graph as an interface definition. Types flow between tools, fetch_file produces a FileRef, commit_edit consumes one and produces a ModifiedFile, run_tests consumes that and produces a TestResult, and the graph itself is enumerable, known at build time, and compilable into the decoder.

fetch_file -> FileRef -> commit_edit -> ModifiedFile -> run_tests -> TestResult

Once the graph is an IDL, the type errors become ungeneratable: the agent cannot call commit_edit on a file it never fetched, because the required input type does not exist yet in the conversation state. That is constrained decoding applied to the right object, the interface between tools, instead of the free-form text flowing around them. The same move lets you define the agent's language subset explicitly, listing the endpoints it may fetch and forbidding the tools that hand over the machine, like child_process; writes stay limited to declared outputs. Compile that subset into both the grammar and the runtime. Enumerable things get compiled; open things get bounded.

Budgets, audits, and the governance payoff

The capability boundary is not hypothetical, the vendors are shipping it. Walmart's Agent Profiles give each agent its own spending cap, approval modes, and ledger, and OpenAI's Practices for Governing Agentic AI Systems codifies action-space constraints, approvals, monitoring, and interruptibility. These are the operational face of the same principle: the interesting governance question is not what the model did, but what the system allowed it to attempt.

A compiled decision space is diffable and reviewable. When a policy changes, you review a capability set or a tool graph, not a transcript of model behavior. Governance shifts from asking "did the agent behave?" to asking "did we specify the allowed behavior correctly?", and the second question has a deterministic answer.

What the boundary cannot do

The capability boundary is also only as good as its spec, and the spec has a hole you should name. A capability set that includes a money tool and a web tool is still unsafe if the money tool's arguments are open-ended: the refund amount is an integer, and nothing at the boundary knows 499.99 violates the two-hundred-dollar rule unless the rule is compiled into the tool interface itself. This is why the two mechanisms are not rivals. Capabilities govern which tools exist. Decoding constraints govern which arguments those tools can receive, and the policy lives in both places, as a capability for selection and as a schema for arguments.

The third layer is judgment, and no amount of compiling makes it enumerable. Whether this customer is genuinely a VIP is a semantic question about the world, and the answer changes in real time. That is the honest place for a probabilistic filter, as the final layer, with its failure rate named and accepted. Keep the classifier, but stop calling it a control.

Move the boundary, don't pray harder

The refund example ends the way it should: the fix is not a better classifier, it is removing the refund from the capability set for that conversation until a second approval exists, and constraining the amount field so the policy is in the schema. The classifier stays, as the last filter, and everyone knows it is a filter.

That is the layered answer the agent-safety discussion keeps circling. Constrain in the decoder where the space is enumerable, including the tool graph itself. Apply capabilities in middleware where it is not. Keep classifiers as the final filter, and say plainly which layer you are relying on for each guarantee. "Will not" is a hope you pay for in retries. "Cannot" is an architecture you review in a diff. A guardrail is something you can drive past; a boundary is something the system cannot cross. The difference is when the decision is made, after the token is sampled or before it exists.
