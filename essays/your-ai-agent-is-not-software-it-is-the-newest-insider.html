Your AI Agent Is Not Software. It Is the Newest Insider.

AI agents are acquiring the access and autonomy to act inside our systems. Securing them requires a different operating assumption. We cannot rely on a model's apparent competence, stated intentions, or good behavior to protect the resources it can reach.

On October 19, 2026, Microsoft made a pointed claim about the security implications of AI agents. Agents, it argued, should be treated as a new kind of insider. The company announced an expansion of its security work around agentic systems, including Guardian Agents within Project Perception and additional controls for its enterprise environment.

The most consequential part of the announcement was not the product launch. It was the change in the question security teams need to ask.

For years, software security has focused on whether a system can be entered, exploited, or operated by someone who should not have access. AI agents complicate that model. An agent may authenticate with valid credentials, read an authorized mailbox, call a sanctioned API, or modify a repository it was explicitly allowed to access. The incident may begin with no stolen password and no breached perimeter. The system can fail because an agent with legitimate access takes an action its operator did not intend.

That is what makes the insider analogy useful. An agent does not need human motives to create insider risk. It needs access, the ability to take actions, and a path from an instruction or environmental signal to an unintended outcome.

Microsoft CEO Satya Nadella framed the underlying design principle as separating the supply of intelligence from the authority to act on it. A model can propose a course of action. The surrounding system must decide whether that action is permitted, under the current conditions, with the current identity, against the particular resource.

Intelligence should not automatically confer authority.

This principle applies well beyond Microsoft 365. It matters wherever an agent can use credentials, access private data, invoke tools, change code, send messages, or trigger operations. The central security question is no longer simply whether the model is good. It is whether the system remains safe when the model makes a mistake, is manipulated, or behaves in a way its designers did not anticipate.

Microsoft's argument is worth examining on its technical merits, independent of its commercial interests. The company is selling products designed to address the risks it is describing. That deserves scrutiny. But the underlying problem extends beyond any one vendor, model, or platform.

The old security model was built around different assumptions

Traditional security architecture is not as naive as the phrase perimeter security suggests. Mature organizations already account for malicious insiders, compromised accounts, excessive privileges, lateral movement, and misuse by authorized users. Zero-trust architecture explicitly challenges the assumption that being inside a network should confer trust.

The problem is not that these controls are irrelevant to agents. The problem is that agentic systems put pressure on the assumptions behind how those controls are implemented.

An ordinary application generally follows a defined execution path, even when it contains bugs or responds differently to different inputs. A human employee can misunderstand an instruction, but their actions are constrained by human attention and working speed. An AI agent can interpret a request, break it into subtasks, consult external material, select tools, act on the results, and repeat the process. It can do this quickly and with limited supervision.

The agent may be operating exactly as its software permits while producing an outcome no one intended.

Consider an agent authorized to summarize a project mailbox and update an internal knowledge base. It can legitimately read messages and write documents. One email contains an instruction that appears to be part of the work but is actually a prompt injection. It tells the agent to include confidential information in its summary and send the result to an external address.

The email is data. It should not have authority to redefine the agent's task. But an agent that fails to distinguish untrusted content from trusted instructions may treat it as a command. If the agent also has permission to send external email, the failure can progress from manipulated interpretation to an actual disclosure.

No attacker needs to break into the mailbox. The dangerous action can travel through an authorized identity and an authorized tool.

This is the overlap between conventional security and the agent problem. Identity controls, least privilege, network segmentation, monitoring, and data-loss prevention remain necessary. What changes is the need to apply them to systems whose behavior is shaped by model reasoning and untrusted natural-language inputs.

The OWASP GenAI Security Project's 2026 Top 10 for LLM Applications identifies prompt injection, sensitive information disclosure, and excessive agency among the leading risks. These categories describe different stages of a potential failure. Malicious content can influence the model, the model can propose an unsafe action, and excessive permissions can allow that action to cause real damage.

The security boundary must therefore sit outside the model. The model can help determine what action appears useful. It should not be the sole authority that determines whether the action is allowed.

Why agents make the insider problem harder

Several characteristics make agentic systems particularly challenging to secure.

They can act at machine speed

An agent can chain many operations together without pausing for a human to inspect each one. A faulty decision can trigger a sequence of tool calls, file changes, API requests, and communications before anyone notices.

The danger is not merely that the model responds quickly. It is that the consequences of one mistaken decision can propagate through an automated execution loop.

This makes detection and containment timing important. A control that identifies suspicious activity after an agent has completed a task may help an investigation, but it may be too late to prevent the damage.

Their access often exceeds the requirements of the current task

Agents are frequently given broad credentials because broad access is convenient. A coding agent may receive write access to an entire repository when it needs to modify a small set of files. An assistant may be connected to a complete mailbox when a task requires reading messages from one folder. A research agent may have access to a browser, shell, file system, and cloud account simultaneously.

This is a familiar security failure: excessive privilege. Agentic execution makes its consequences harder to predict because the model chooses which available tools to use in response to evolving context.

The relevant question is not whether an agent is allowed to access a resource in general. It is whether the agent needs that access for this specific operation, at this point in the task.

Their behavior is sensitive to context

A language-model-driven agent adds a source of variability beyond conventional application logic. Instructions, retrieved documents, tool results, conversation history, and other context can influence which action it selects.

A system prompt saying "never disclose secrets" is not an access-control mechanism. It is an instruction to the model. It cannot replace a system that prevents secrets from being read or transmitted when policy forbids those operations.

This distinction matters in prompt injection. An attacker may place instructions in a webpage, document, email, code comment, or tool response. The agent consumes that content while pursuing a legitimate goal. If it treats the injected text as authoritative, an attacker can influence its behavior without controlling the model or the agent's original account.

The right response is not to assume every prompt injection will succeed. It is to design the system so that a model-level failure does not automatically become a security incident.

They multiply the number of actors

An organization may deploy agents built with different frameworks, connected to different data sources, owned by different teams, and running under different identities. Individual employees may also create local agents and connect them to tools outside centralized governance.

Microsoft said its Defender capabilities were expanding to cover 60 local agent types, including agents such as Claude Code, Codex, and OpenClaw. That figure illustrates the operational challenge, although it is a vendor-reported figure about supported agent types, not a measure of all deployed agents across the industry. See Microsoft's announcement.

Every agent that can take action creates questions of ownership, authorization, observability, and containment. At scale, security teams need an inventory and a consistent way to enforce policy. They cannot rely on knowing which agent is running in every conversation or developer session.

An insider does not need malicious intent

The insider analogy can be misunderstood. It does not require us to believe that an AI agent possesses human motives, loyalty, resentment, or an intention to steal information.

In security terms, the useful feature of an insider is their position relative to protected resources. They have legitimate access. Their actions can violate policy, whether through malicious intent, negligence, manipulation, error, or compromise.

The same distinction applies to an agent.

There are at least three ways an agent can create insider-like risk.

Unintended action. The agent misinterprets a task, produces an incorrect plan, or chooses a damaging operation while trying to accomplish the user's goal.

Manipulated action. Untrusted content influences the agent to pursue a different goal, reveal information, or invoke tools in ways the user did not authorize.

Compromised execution. A tool, extension, runtime, credential, or other component in the agent's environment is compromised, allowing actions that the operator did not expect.

These failure modes require different technical responses, but they share a principle. The system cannot make its security depend on the agent always interpreting the task correctly.

The economics of conventional insider risk underline the importance of that principle. IBM's Cost of a Data Breach Report 2025 reported that malicious-insider attacks had the highest average breach cost among the initial attack vectors it studied, at $4.92 million. This is a measure of conventional malicious-insider breach costs in IBM's research. It is not evidence that AI agents cause comparable losses or that insider incidents account for a fixed percentage of all breaches.

An agent is not an employee. Treating it as an insider is a way to reason about access and risk, not a claim about its psychology.

A useful analogy is a highly capable contractor who can act quickly across several company systems but does not reliably understand the business context behind every instruction. You would not solve that risk by asking the contractor to promise to behave well. You would define their permissions, monitor consequential actions, and ensure they could not bypass controls governing sensitive operations.

The same principle applies to AI agents, with one major difference. The agent may need to interpret a large volume of untrusted content, and it can act through tools at machine speed.

An industry-wide shift is taking shape

Microsoft's October announcement did not create the problem or establish the only response. It made a broader shift in agent security more visible.

Several major AI and infrastructure companies have been developing approaches that emphasize runtime controls, explicit boundaries, and limits on what agents may do.

CompanyRelevant workSecurity direction
MicrosoftProject Perception, Guardian Agents, Entra Agent ID, Agent 365Agent discovery, identity, risk signals, policy enforcement, and containment
AnthropicZero Trust for AI AgentsApply zero-trust principles instead of assuming an agent's actions are trustworthy
Google DeepMindSecuring the Future of AI AgentsResearch and guidance on securing agentic systems and their interactions
NVIDIAOpen Agent Safety PlatformRuntime boundaries, policy enforcement, and monitoring of agent execution

These are not identical offerings. Some are enterprise products, some are research and guidance, and others are platform components. It would be misleading to present them as equivalent products or as proof that the industry has settled on one architecture.

Their overlap is more important than their branding. Agent security cannot be reduced to selecting a stronger model. The system surrounding the model needs its own security architecture.

Microsoft's proposed approach connects agent identity and activity with signals from identity, data, endpoints, cloud infrastructure, network traffic, and runtime behavior. Its aim is to detect risky behavior and respond with controls that range from restricting an action to revoking access or isolating an agent. The company's October announcement describes these capabilities as part of its broader Project Perception and Agent 365 efforts.

Anthropic's zero-trust framing addresses the same basic problem from a different direction. Google DeepMind's work examines the security challenges emerging as agents gain access to tools and take more complex actions. NVIDIA's platform initiative focuses on infrastructure for controlling and observing agent execution.

The convergence suggests that the security problem is moving from theoretical concern toward operational design. It does not mean every deployed agent is dangerous, or that every vendor's control system is mature enough for every workload. It means that responsible deployment requires a plan for what happens when an agent behaves incorrectly or is manipulated.

That is a more durable conclusion than any individual product announcement.

The controls must sit outside the model

What would it mean to build a system that does not rely on the model to enforce its own safety?

At minimum, the system needs independent controls. They should constrain actions even when the model's interpretation or plan is wrong.

Give the agent a real identity

An organization should be able to answer basic questions about every agent. What is it? Who owns it? What resources can it access? Which tools can it invoke? Which credentials does it use? What policy governs it? Where are its actions recorded?

Without agent identity, activity may be attributed only to the human user, service account, or machine underneath it. That weakens the audit trail. It becomes difficult to distinguish the person who requested an operation from the agent that executed it, especially when the agent performs several steps or calls another agent.

Identity should connect an agent to an accountable owner and a defined scope of authority. It should not be treated as a label that automatically grants access.

This is also the direction of work from the National Institute of Standards and Technology, which has been examining how existing identity standards and authorization practices can be applied to software and AI agents.

Use task-scoped permissions

Least privilege is more useful when applied to the current task rather than configured only at the agent's initial setup.

An agent that needs to inspect a repository should not automatically receive permission to push code. An agent preparing a draft email should not automatically be permitted to send it. An agent that reads customer records should not inherit permission to export them.

Permissions should be narrow, revocable, and limited in duration wherever possible. A system may grant temporary access for a particular operation, require separate authorization for a higher-risk action, and remove access when the task ends.

This does not require elaborate dynamic authorization in every small application. A simple agent can achieve a great deal with a narrowly scoped operating-system account, read-only credentials, a restricted workspace, and a limited set of tools. The control should match the risk.

Put a policy-enforcement layer between reasoning and action

The model should not be the final authority over whether its tool call is permitted.

A tool gateway or equivalent enforcement layer can evaluate an action before execution. Depending on the system, it can check the agent's identity, the user's authority, the resource being accessed, the action type, the task's scope, and relevant risk conditions.

For example, the model might propose sending a file to an external address. The policy layer can inspect the destination, classify the data, check whether external transmission is allowed, and deny the operation or route it for approval.

The policy layer should not simply ask the same model whether the action is safe. It needs enforceable rules and access to the relevant system state. Model-based analysis may add a risk signal, but it should not be the only line of defense.

Monitor behavior and contain failures

Static permissions answer what the agent is allowed to do. Runtime monitoring asks whether the way it is operating remains consistent with the task and the expected pattern of use.

A research agent suddenly attempting to enumerate local secrets should trigger a different response from one reading approved web pages. A coding agent that unexpectedly accesses environment files, modifies unrelated repositories, or attempts outbound network connections may need to be stopped and investigated.

A risk score can help prioritize attention, but it should not be mistaken for proof of malicious behavior. Useful responses include blocking a particular operation, requiring additional approval, removing a credential, revoking a session, stopping the agent, or isolating its runtime.

The system should also record enough context to investigate what happened. Logs need to connect the request, identity, policy decisions, tool calls, resource changes, and outcomes. Model reasoning or traces may help diagnosis, but sensitive reasoning traces require careful access and retention controls.

Greater visibility into model behavior is not a substitute for controls that can stop actions. The enforcement layer needs to remain effective even when the agent cannot explain its behavior accurately or is actively attempting an unauthorized operation.

Make the runtime a boundary, not a suggestion

An agent executing shell commands, reading files, installing packages, or interacting with external services needs containment appropriate to those capabilities.

A sandbox, restricted container, virtual machine, or other isolation mechanism can limit the consequences of a failure. Network access can be restricted. Sensitive host paths can be withheld. Credentials can be kept outside the agent's ordinary workspace. Filesystem writes can be confined to selected directories. Dangerous operations can require a separate, explicit approval path.

A sandbox is not sufficient by itself. An agent with a powerful cloud token can still do damage through an allowed network connection, even if its local filesystem is isolated. Runtime containment must be combined with narrow credentials and authorization checks at the systems the agent can reach.

The design goal is to prevent a mistake in the reasoning layer from becoming unrestricted authority in the execution layer.

The commercial incentive deserves scrutiny

Microsoft's announcement also creates a legitimate commercial question. Microsoft is positioning agent security as a major enterprise need while offering products designed to address it. Its business relationships include investments in OpenAI and Anthropic, and OpenAI is a Microsoft cloud customer. TechCrunch highlighted these relationships in its coverage of Microsoft's announcement.

Microsoft's current published list pricing puts standalone Agent 365 at $15 per user per month, while Microsoft 365 E7 is listed at $99 per user per month and includes Agent 365. These are prices for particular Microsoft offerings, not a measure of the total cost of securing an agent deployment. See Microsoft's Agent 365 licensing FAQs.

This gives Microsoft an obvious incentive to define agent security as a new, urgent category of enterprise spending. That incentive should influence how its claims are evaluated.

It does not, by itself, make the technical argument false.

Security products routinely address risks that their vendors also have a commercial interest in describing. The appropriate response is to examine the threat model, the effectiveness of the controls, the limits of the product, and whether the customer can independently verify enforcement.

Can an administrator see every agent that falls within the product's coverage? Can the system distinguish an agent from its owner and from the credentials it uses? Can policies block an operation before it happens? Can the customer investigate an action after the fact? What happens when the agent uses a third-party tool or runs outside the vendor's managed environment? Can the security team revoke access without relying on the agent to cooperate?

These are better questions than whether Microsoft is overstating the danger.

A product that identifies agents but cannot reliably constrain their actions solves an inventory problem, not the entire security problem. A product that detects suspicious activity only after an agent has transmitted sensitive information provides visibility but not prevention. A platform that enforces policies only inside its own ecosystem leaves gaps wherever the agent operates beyond that boundary.

The right response to vendor claims is neither automatic acceptance nor automatic dismissal. It is independent evaluation against concrete security requirements.

What users of AI agents can do today

You do not need to build an agent platform or run a security team to reduce agent-related risk. You do, however, need to be deliberate about which tasks you delegate and what authority you give an agent to complete them.

Most users cannot control how an underlying model was trained or how a hosted service implements its security architecture. They can control their choice of tasks, connected accounts, available tools, approval settings, and the amount of supervision a task receives.

That is a useful starting point.

Match autonomy to the consequences of the task

Not every task requires the same degree of trust or supervision. Summarizing a public article is different from sending a confidential report to a customer. Drafting a database migration is different from running it against production.

Before delegating a task, consider three things. What could the agent access? What could it change? What would happen if it misunderstood the request or followed malicious instructions embedded in the material it reads?

Use the answers to decide how much autonomy to grant.

Task categoryExamplesSensible starting point
Low consequenceSummarizing public information, brainstorming, classifying non-sensitive textAllow work with minimal supervision
Moderate consequenceEditing project files, updating internal documents, preparing code changesRestrict the workspace and review proposed changes
High consequenceSending external messages, deleting data, moving money, changing permissions, deploying to productionRequire explicit authorization or retain the consequential step for yourself

These categories are contextual, not universal. Editing a personal note may be low risk. Editing a legal record or production configuration may be high risk. The appropriate level of autonomy depends on the resources involved and the possible consequences of an error.

Give an agent more freedom when mistakes are easy to detect and reverse. Reduce its freedom when mistakes are difficult to detect, expensive to reverse, or damaging to other people.

Define the task's boundaries before the agent starts

Broad requests leave room for an agent to make assumptions. That flexibility can help with research and analysis, but it becomes problematic when the agent can take consequential actions.

Instead of saying, "Clean up my project repository," specify what the agent may inspect, what it may change, and where it must stop.

A practical task contract can be short:

  • Objective: What outcome should the agent produce?
  • Scope: Which files, accounts, resources, or sources may it use?
  • Permitted actions: What may it read, create, update, or execute?
  • Prohibited actions: What must it not access or change?
  • Approval points: Which actions require you to intervene?
  • Completion criteria: What should the agent deliver, and how will you verify it?

For example, a coding agent could be asked to inspect a repository, implement a narrowly defined feature, run the relevant tests, and present a diff. It should not commit, push, deploy, modify unrelated files, or access production credentials without separate authorization.

This task contract helps both the user and the agent. It makes the intended scope explicit and gives the user a concrete basis for reviewing the result.

There is an important limitation. Writing "do not deploy" into a prompt does not technically prevent deployment if the agent retains unrestricted access to deployment tools. For consequential restrictions, configure permissions and approval mechanisms to enforce the boundary. If the platform cannot enforce the restrictions you need, reduce the agent's access or choose a different way to perform the task.

Treat connected accounts as delegated authority

When you connect an agent to email, cloud storage, a code repository, a calendar, or a browser session, you are giving it a path to act within those systems. The permissions behind that connection matter more than the apparent simplicity of the integration.

Before enabling a connection, ask whether the agent needs read access, write access, or both. Can it access a specific folder or repository instead of an entire account? Can you restrict it to a project-specific credential? Can you remove access when the task is complete?

Prefer narrow, task-specific access over persistent, account-wide privileges. Use read-only access when the task requires only reading. Avoid supplying broad API keys or administrator credentials merely because doing so makes setup easier.

A research assistant that gathers source material does not normally need permission to send email. A coding agent that reviews a pull request does not automatically need permission to merge it. An agent that prepares an expense report does not necessarily need authority to approve the payment.

Assume content the agent reads may contain hostile instructions

An agent may encounter instructions in places where you would ordinarily expect data. A webpage might tell it to reveal information from previous context. An email might instruct it to forward a private attachment. A document or code comment might contain text designed to redirect its behavior.

This is the basic problem behind indirect prompt injection. The content the agent is processing may attempt to change what the agent does, even though that content has no legitimate authority to change the user's original request.

You do not need to treat every document as malicious. You should, however, avoid assuming that content is trustworthy merely because the agent found it during a legitimate task.

When an agent works with external material, keep the material's authority separate from your own instructions. Do not permit a webpage, email, or retrieved document to authorize unrelated tool calls, disclose secrets, or expand the agent's permissions.

For research tasks, check important claims against independent sources. For email and document workflows, be cautious when the material asks the agent to send information elsewhere, open unexpected links, run commands, or reveal data unrelated to the task.

Most importantly, do not rely on an instruction such as "ignore malicious prompt injections" as your only protection. Use restricted permissions and tool access so that a failure to recognize hostile content does not automatically result in an unauthorized action.

Put approval gates around consequential actions

Human oversight does not require watching every token the model generates or approving every minor operation. It means retaining control over decisions where the consequences justify intervention.

For common workflows, establish a clear distinction between preparing an action and executing it.

An email agent can research an issue, draft a response, and identify recipients without automatically sending the message. A coding agent can implement a change and run tests without deploying it. A finance assistant can calculate a payment and prepare the transaction without transferring the money.

These workflows preserve much of the efficiency of automation while keeping the final consequential decision under deliberate control.

Approval gates work best when the action is presented clearly. Before approving a sensitive operation, you should be able to see what the agent intends to do, which resource is affected, what information will leave the system, and what the expected consequences are.

A vague approval request such as "May I proceed?" is much less useful than "May I send this report, containing these attachments, to these external recipients?"

Approval should not become a ritual. If the user cannot understand the proposed action well enough to evaluate it, the system needs to provide better information or reduce the scope of the operation.

Verify what the agent actually did, not just what it says it did

An agent's summary of its work is not independent evidence that the work was completed correctly.

An agent may report that a test passed when it ran a different test suite. It may claim that it updated a document when the change was not saved. It may say that a message was sent even though the operation failed. It may complete the requested change while modifying unrelated files.

Verification should match the task.

For coding work, inspect the diff, examine test output, and run critical tests independently. For research, inspect cited sources rather than relying only on a generated bibliography. For document edits, compare the resulting file with the original. For administrative actions, check the destination system to confirm what changed.

This principle becomes more important as the agent gains autonomy. When a system can execute multiple steps without supervision, the final answer may hide intermediate mistakes or side effects that matter to the user.

Ask the agent to report what it changed, which operations failed, which claims remain uncertain, and what still needs review. Then verify the important parts independently.

The purpose is not to distrust every output. It is to preserve an evidence trail between the requested outcome and the actual result.

Limit unattended execution

Scheduled agents and long-running assistants need additional boundaries because their actions may continue after the user has stopped paying attention.

A recurring research agent, for example, may be safe when it reads public websites and saves summaries to a dedicated folder. If it can also execute arbitrary commands, send messages, or change unrelated files, an unexpected input could have consequences well beyond the intended research task.

Set limits appropriate to the workflow. Restrict which resources the agent can access, how often it can run, how much work it may perform in one cycle, and which actions it may execute unattended. Use destination allowlists where practical. Keep failures and unusual activity visible. Ensure that a scheduled job can be disabled without having to interact with the agent itself.

For multi-agent systems, be especially careful about delegated authority. One agent should not automatically inherit another agent's access just because it receives work from that agent. Each handoff should preserve the original task's boundaries and restrictions.

Unattended execution should be treated as a deliberate increase in autonomy, not simply a convenience setting.

Know how to stop the agent and revoke its access

Before relying on an agent for a consequential workflow, understand how to interrupt it.

Can you stop the current run? Disable future scheduled executions? Disconnect the relevant integration? Revoke the token or credential the agent uses? Determine which actions have already completed?

These are different operations. Stopping an agent may prevent future actions without undoing actions already taken. Disconnecting an integration may not invalidate a credential that was separately copied or stored. Deleting a conversation may not delete files the agent created in another system.

If you suspect an agent has exposed a secret or taken an unauthorized action, stop further execution, revoke or rotate the affected credentials, inspect activity logs, and check the systems it could have reached. If it sent information externally or modified shared resources, address those consequences separately.

The ability to recover is part of safe delegation. A system is difficult to trust when the user cannot reliably identify what it did, prevent it from continuing, or revoke the authority it holds.

A practical rule for everyday use

Before giving an AI agent a task, ask three questions.

What am I allowing it to access? What am I allowing it to change? What is the worst plausible outcome if it gets this task wrong?

Those questions do not require specialized security knowledge. They encourage users to think about agent use in terms of access, authority, and consequence rather than capability alone.

The aim is not to avoid AI agents or require human approval for everything they do. It is to delegate work without surrendering more authority than the task requires.

An agent can be useful without being trusted with unrestricted access. Users can benefit from its ability to interpret information and perform work while retaining control over sensitive data, external communications, irreversible changes, and other consequential decisions.

That is the practical meaning of treating an AI agent as an insider. You do not need to assume it will behave badly. You need to be prepared for the possibility that it will.

The objections are worth taking seriously

The insider framing is useful, but it is not a complete security model by itself. Several objections deserve serious consideration.

"This is vendor fear, uncertainty, and doubt"

There is an incentive to turn a difficult technical problem into a new product category. The language around agentic insiders can help vendors sell inventory, identity, monitoring, and governance tools.

But the underlying risks do not depend on Microsoft's product strategy. Prompt injection, excessive agency, sensitive information disclosure, and unsafe downstream execution are recognized categories in the OWASP GenAI security work. These are risks that can affect systems from many vendors, not just those using Microsoft products.

The practical test is whether a proposed control reduces a demonstrable risk. A security team should not buy a product simply because an announcement uses alarming language. Nor should it ignore a risk because a vendor is selling a response to it.

"Agents are not humans, so the analogy is misleading"

This objection is correct if the analogy is interpreted literally. An AI agent is not a human employee. It does not need to possess a human concept of loyalty, intention, or misconduct for its actions to create a security problem.

The analogy is valuable because it directs attention to the agent's relationship with protected resources. Does it have legitimate access? Can it perform actions that violate policy? Can those actions cause harm before someone intervenes?

"Insider" describes the position from which risk can arise. It does not explain the underlying cause of every failure. Security design still needs to distinguish model errors, prompt injection, compromised tools, stolen credentials, unsafe configurations, and conventional software vulnerabilities.

"Most failures are caused by bad configuration"

Poor configuration is often part of the problem. An agent cannot send a private file using a credential it does not possess, and it cannot modify a protected resource if the enforcement layer reliably denies the operation.

But configuration is not a complete answer. An agent's behavior is influenced by context, and a configuration that appears adequate for normal usage may expose unexpected paths through a long chain of tool calls. The challenge is to make permissions restrictive enough that an unforeseen path does not automatically become a damaging action.

The insider framing encourages teams to assume misuse can happen and to limit the consequences when it does.

"Dynamic permissions and approvals will slow everything down"

They can. Requiring explicit human approval for every file read, API call, or harmless transformation would make many useful agents frustrating to operate. A system that stops constantly for trivial authorizations may encourage users to bypass safeguards.

The answer is not to add friction indiscriminately. It is to match control strength to consequence.

Reading an approved document may require no extra interaction. Writing into a task-specific workspace may be permitted automatically. Sending confidential material to an external destination, deleting production data, changing access rights, or deploying code may need a separate policy decision or human approval.

For well-understood tasks, pre-approved policies can keep the agent moving without granting it unrestricted authority. For unfamiliar or high-impact actions, the system can pause, narrow the operation, or request authorization.

The goal is not to make every agent slow. It is to prevent convenience from becoming an excuse for unnecessary privilege.

The security boundary is the real product

AI security discussions often focus on the model. Is it aligned? Is it robust against prompt injection? Does it reveal sensitive information? Can it be manipulated into producing dangerous outputs?

Those questions remain important. They are not enough for an agent with the ability to act.

Once a model can read data, execute commands, call APIs, modify resources, or communicate with external systems, security depends on the architecture around it. The model's interpretation is only one step in a sequence that leads to a real-world effect.

An agent should be able to make a mistake without gaining more authority than it was given. It should be possible to deny an operation without asking the model to agree. A compromised or manipulated agent should remain bounded by controls outside its reach. And when something goes wrong, the system should provide enough evidence to understand what happened and contain the consequences.

That is why the insider analogy matters. It moves attention away from whether the model deserves trust and toward the access it has, the behavior it exhibits, and the boundaries that limit its actions.

The phrase "trust the model least" should not be read as an argument that models are useless or that agents should never be trusted with meaningful work. A model can be useful precisely because it can interpret ambiguity, adapt to context, and select actions without a developer writing a fixed path for every possibility. Those capabilities are what make agents valuable. They are also why a model should not receive unrestricted authority simply because its outputs are often good.

A secure system can trust a model to propose an action without trusting it to authorize that action. It can use a model to interpret a request without granting it access to every resource that might help. It can let an agent perform complex work while constraining the permissions, tools, network paths, and side effects available to it.

This is the distinction between capability and authority.

Capability is what the agent can figure out how to do. Authority is what the system permits it to do. A secure design does not assume those two things should always match.

The most capable model in a system should not automatically have the broadest access. A narrow model with highly privileged tools can still create serious risk. A strong model in a tightly constrained runtime can be useful while having limited ability to cause damage. Model quality matters, but it is one variable in a larger security architecture.

The same principle applies to observability. More insight into the model's process can help teams understand unexpected behavior, but an explanation of what happened is not a substitute for preventing an unauthorized action. The control needs to be capable of saying no independently.

The model supplies intelligence. The system grants authority. Security depends on keeping those two things separate.
