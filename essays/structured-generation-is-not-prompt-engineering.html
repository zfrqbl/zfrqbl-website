Structured Generation Is Not Prompt Engineering

An agent is told to produce a phone number, and it writes "I'm sorry, I can't help with that." Ten samples from Mistral-7B-Instruct, ten useless outputs, a mix of refusals, pleasantries, and wrong formats. The model is not bad at language. It cannot hold a format contract that was imposed only as prose.

The reflex is to fix the prompt. Add another sentence telling the model what the output should look like, maybe two, maybe a numbered list of requirements. Every fix is unverifiable guesswork. No unit test can assert that "please be more creative" worked, and the evidence for a prompt change is a sample of one. This is where agents that write or improve their own prompts get stuck, because a prompt is prose, and prose changes have no test harness.

Structured generation is the alternative, and it is not a library feature. It is a different development methodology. You write a structure that matches real data you already trust, you iterate on that structure when the output is boring or wrong, and you debug the constraint instead of the prompt. The dottxt walkthrough, turning Mistral-7B's yapping into a run of varied, realistic-looking (206) 494-3216s with three regex edits and zero prompt changes, demonstrates the core claim, that structured generation converts LLM work from unverifiable prompting into conventional software engineering, where changes are testable, failures are localizable, and improvements survive an eval suite.

The yapping problem

Start with the unstructured baseline. Ten samples from an unconstrained Mistral-7B-Instruct produce zero usable phone numbers. The task was trivial, a phone number in a standard format, and the model failed it completely, not because it is a bad model but because nothing constrained it. The format contract existed only in prose, and prose is where LLMs are least reliable.

This matters most for agents that write or improve their own prompts. Such an agent edits its own instructions and judges the result by whether the output looks better. That loop has no ground truth. The output changed, but did it change because the prompt improved, or because sampling is noisy? You cannot tell from a sample of one, and the agent cannot either. Prompt engineering is the only discipline I know where a change is accepted on the strength of a single anecdote, and it is a discipline we are now asking agents to practice on themselves, unsupervised, at scale. An agent rewriting its own instructions with no measurement to accept or reject the edit is a feedback loop with the error signal removed.

Structure is a contract, not a suggestion

Constrained decoding is the mechanism that ends the guesswork. Compile a regular expression to a finite-state machine, then at each sampling step drop every vocabulary token that cannot extend the current prefix toward a valid match. The matcher becomes a generator, and you are running a regular expression in reverse. The machine only ever proposes tokens that keep the output on track to satisfy the pattern.

The heavy part can be precomputed. Willard and Louf showed in their grammar-constrained decoding work that the FSM and the vocabulary masking can be built before generation starts, which makes guided generation nearly free at inference time. The guarantee is enforced online, during the sample; the work that makes it cheap is done offline, once. That is the property that makes the whole approach practical, because a guarantee that doubled inference cost would never leave the lab.

Start with real data

The development loop dottxt demonstrates is unglamorous and it works. Take a known-good example, the Seattle Public Library's number, (206) 386-4636. Write a regex that matches it:

import re
phone_re = re.compile(r"\([0-9]{3}\) [0-9]{3}-[0-9]{4}")
assert phone_re.fullmatch("(206) 386-4636")

Match-then-generate becomes your test harness. You verify the structure against a real sample before you generate a single token, and the same assertion that validated your example validates every future sample, because the sampler is bound to the same expression.

Generation artifacts become visible this way too. Run an unstructured model against a loose pattern and you get 555-1234 repeats, numbers that look fake because they are, pulled from training-data stereotypes rather than any property of the constraint. The regex allowed them, because a loose regex is a loose contract. The model filled the constraint's slots with what it knows, which is why the constraint has to be precise.

Iterate on structure, not on the prompt

The dottxt post walks three revisions of the phone regex, and the arc is worth holding onto because the prompt and temperature never change across any of them. First attempt, the plain \([0-9]{3}\) [0-9]{3}-[0-9]{4}. It produces numbers, but they cluster around fake exchanges:

phone_re = re.compile(r"\([0-9]{3}\) [0-9]{3}-[0-9]{4}")

Second revision, disallow 5 in the exchange and a leading 1 in the line number:

phone_re = re.compile(r"\([2-46-9][0-9]{2}\) [02-9][0-9]{2}-[0-9]{4}")

That kills the 555 and 1-800 look. Third revision, tighten the distribution further until ten distinct, plausible numbers come out. Each step is a one-line diff with a rerun behind it. Russ Cox's point about regular expressions applies directly here, that a regex is a precise definition of a set of strings rather than a heuristic. You can read the constraint and know exactly which outputs are admitted, which is why iterating on it converges and iterating on a prompt does not.

Every revision is a code change, a diff with a verification step, and every verification step is a rerun. The evidence for each change is a batch of samples, not one output that happened to look better. That is why this is engineering and prompting is not. With prompts, the change is prose and the evidence is a sample of one. With structure, the change is a diff and the evidence is an eval run. An agent that improves its own prompts can only converge if its improvement loop has this property, a way to measure whether a change actually helped.

Debug the generator like a program

The hinge of the whole post is a bug that looks like nothing. phone_regex_3_error looks right and passes a naive match check, but it silently truncates the last digit. The pattern admits (206) 386-463 as a valid prefix and generation stops there. A partial match is not compliance, and anchored, full matching catches what naive matching misses.

This is the debugging mode that structure enables and prompting cannot. When output violates the constraint, the bug points at one line, the regex or the schema or the grammar. The failure is localizable. With prompting, an "improvement" that makes output worse offers no pointer at all, because there is no invariant being violated, just prose that changed. Improvements brought on by prompting are often illusory; structure mismatches point at the exact line that is wrong. An LLM program has assertable invariants. A prompt has anecdotes.

Structure is everywhere, beyond JSON

Structured generation does not stop at JSON. The aesthetic constraints in the phone example, disallowing fake exchanges, making digits feel random, those are constraints too, just expressed in a regex instead of a schema. And once regular expressions top out, the same loop scales to context-free grammars. EBNF, the notation from every compiler course, is expressible as a grammar, and the same masking machinery handles it.

Ordinary programming-language tooling becomes relevant again. BNF and EBNF from the compiler curriculum, parser toolkits like Lark and parsimonious, schema-first patterns that are already normal everywhere else in the stack, Pydantic, Zod, structured generation is the LLM finally joining that world instead of floating in a prose-only universe above it. The techniques were developed over decades of systems that had to parse precisely, and they apply unchanged to systems that must generate precisely.

The shift matters for teams holding agents together with long prompts and hope. Once you treat output as a grammar problem, the tooling from a compiler course becomes an asset list, a grammar for the output and a parser to check it. A generator that cannot violate the grammar rides on the same machinery. None of that exists for prose, and none of it needs a larger model, only the discipline of writing the structure down.

Agents can be software engineers again

The research backup is stronger than a blog post. Grammar-constrained decoding is a coherent program, not a hack. Geng and colleagues showed it beating task-specific finetuned models on information extraction and entity disambiguation with zero finetuning, one ordering that matters. Structure constraints carry the correctness, and the LM supplies the smarts. The structure is not compensating for a weak model; it is the repeatable, testable part of the system, and the model is the flexible part.

For an agent that writes or improves its own prompts, the implication is direct. The prompt is where the agent's behavior lives today, and it is the least testable object in the system. Structure is where behavior can be pinned down and verified. The agent that can rewrite a regex, rerun an eval, and keep the changes that pass, has a development loop. The agent that only edits prose has a prayer.

The point is not that prompts are worthless. It is that a prompt-improving agent has no way to tell a real improvement from a lucky draw. Sampling is noisy twice over. The model changes its output run to run, and the quality judgment is itself an LLM call. A self-modifying agent that cannot measure its own changes is a feedback loop running on anecdotes. Give it a structure to enforce, a regex or a schema, and the measurement problem becomes mechanical. Pass or fail is decided by the constraint, not by a second opinion from the same model that wrote the output.

The line between the two disciplines is measurable. A structure change either admits a different set of outputs or it does not, and you can prove it with a test. A prompt change admits a different distribution of outputs, and the only way to see it is to sample and squint. When the system doing the changing is an agent, running unsupervised and at scale, that difference stops being a preference and becomes a safety property. Next time one of your agents is tempted to add a fourth paragraph to its system prompt, give it a regex and a known-good example instead. Yapping is a modeling problem; structure is a code problem. One of them has a test harness.
