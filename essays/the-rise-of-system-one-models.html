The Rise of System One Models

Software doesn't need a model that writes. It needs a model that decides, and for that job a generative model is the expensive way to get a boolean.

Models have been superhuman at chat for years, and the industry still can't point to where all the automation went.

Diogo Almeida, who helped build the instruction-following research that became ChatGPT, spent four years on that question before he left OpenAI. His answer, shipped in September 2026 as TypeSafe AI's Jev, is that the bottleneck was never raw intelligence. It's the interface. A model that replies in prose is an awkward component to build software on, because software doesn't consume sentences. It consumes values.

The model class TypeSafe calls System One is named after the fast, intuitive thinking in Kahneman's Thinking, Fast and Slow.

System One models fill in the specific role of making decisions in LLM-powered applications operation. What makes them unique is token economy in terms of input vs output tokens and processing speed at scale. Using a general-purpose generative model to fill that role wastes tokens and process efficiency. These  decision models hand you the decision while a generative model hands you a string you then have to run through another LLM call or a scripted regex parser to get the desired result.

Strings are the wrong interface for software

Every pipeline I've built has the same point of friction: somewhere a language model writes prose and my code reads it back. The application wants a decision about keeping or deleting an email, or classifying a ticket as escalation to a human. A model like Opus or Luna generates a full paragraph containing the full reasoning and the actual one-word decision. This means all such LLM responses are automatically routed through a parser to extract just that one-word decision. Triaging an inbox with thousands of unread emails with this pipeline means wasted token and slow response because of additional hops in the flow.

The waste shows up in four places at once. Output tokens cost three to eight times the input price on most providers, and a classification answer is mostly output. The response is a string, so it has to be parsed, and JSON mode wraps the real answer in a structure that can multiply the token count five to ten times on a small task like email classification. Then the value has to be validated against a Pydantic schema, because I can never fully trust  a generative model from emitting a response I never defined or expected. And when any of that fails (and it will), I have retry blocks, which costs another full generation. Add it up and a task whose substance is a single yes or no bills like a small essay.

There's a fifth cost that doesn't show on the invoice. A generative model is systematically overconfident. You can ask it for a confidence score and it will give you one, but the number isn't calibrated, so you can't fully trust it. A model that's right 95% of the time but can't tell you which calls are in the other 5% can't be trusted to run unattended. You keep a human in the loop because you have no way to know when the model needs one.

The agent loop makes all of this worse, because an agent makes a decision at every step. This means every decision requires another model call, and the loop is slow and costly because of retries and the overall lack of confidence on the validity of the response. The problem is the same whether your agent writes code or simply classifies emails. A coding agent that routes every request to a frontier model is paying for a full generation on what are often simple lookups.

What a System One model actually is

Jev gives up string generation entirely. Instead of a chat interface, you declare the shape of the answer up front, then call it like a function. You send a state (the context) and a set of questions about that state, and it returns the fields filled in, each with a calibrated probability attached. TypeSafe describes it as a frontier-intelligence function call with unstructured state in and typed probabilistic decisions out.

This design comes with the following three properties that directly or indirectly negate the costs of using generative models for decision making calls.

Parallel sampling. A chat model builds its answer one token at a time, each conditioned on the last. Jev fills every field in a single pass. TypeSafe reports end-to-end response times of 70 to 500 milliseconds against 3 to 329 seconds for frontier models, and you can ask several questions about the same state in one request without meaningfully changing the response time. That's where the 40x to 200x speed claims come from.

Schema conformance by construction. The possible outputs are enumerated before the call, so a type error cannot occur because of a wrong model decision or hallucination. TypeSafe's 0% type-error figure is derived from the construction of the responses.

Calibrated confidence. When this model gives an answer, it also gives a probability. Instead of tuning it for human approval, TypeSafe uses Reinforcement Learning for Calibrated Decisions (RLCD) so those probability numbers are genuinely accurate. If the confidence is high, the accuracy is high. That predictability makes it much easier to use Jev into complex decision-making systems without worrying about any drop in consistency.

The question types map cleanly onto what software actually asks. A Noul answers yes or no and returns the probability the statement is true. A Choice picks from a set of  up to 255 options, and returns a probability per option plus an overall confidence. A Score rates the input against ordered levels like low, medium, high. Keep or drop, route to tier two or tier three, is this urgent: each one is a line of code that returns a typed value.

The token economy of a decision

Now the part that should make you re-read your own invoice. The pricing is the other half of the explosive growth of Jev models.

Jev costs $0.042 per million input tokens, and output is free, because there is no output in the billing sense. TypeSafe advertises it as 238 times cheaper on input than Claude Fable 5.1's $10 per million. A frontier chat model lists around $5 per million input and $25 to $30 per million output. The worse part is that the output is where a classification answer lives.

The math on a single keep/drop decision is small either way. You start noticing the problem when you are making decisions in volume. Let me write the cost function so it's not hand-wavy:

def cost_per_call(input_tokens: int, output_tokens: int,
                  in_price_mtok: float, out_price_mtok: float) -> float:
    """Dollars for one call from token counts and per-million-token prices."""
    return (input_tokens * in_price_mtok + output_tokens * out_price_mtok) / 1_000_000

# A frontier chat model on a keep/drop decision: 600 in, 80 out.
llm = cost_per_call(600, 80, 5.00, 30.00)      # $0.0054
# Jev: same 600 input tokens, no output charge.
jev = cost_per_call(600, 0, 0.042, 0.0)        # $0.000025

print(f"generative LLM: ${llm:.6f} per call")   # $0.005400
print(f"System One:     ${jev:.6f} per call")    # $0.000025
print(f"ratio: {llm / jev:.0f}x")                # ~214x

Run that block at a million decisions a day and the difference stops being trivia. The generative model bills about $5,400 for that volume. Jev bills about $25. Third-party measurements land between the two extremes: one group measured 1,000 eight-way routing decisions at $0.015 on Jev against $0.61 on GPT-5.6 Terra, about 40x. TypeSafe's own workflow evals claim 444.6x cheaper, and LangChain repeats "400x lower cost" on classification tasks. Whatever the honest middle is, it's two orders of magnitude, and it's structural, not a price war.

The gap isn't because Jev is a smaller, cheaper model that happens to be good enough. It's because a generative model bills you for the process of producing prose, and a decision doesn't need prose. Output tokens, parsing, validation, retries, and the uncertainty tax all disappear together because the model was built to not generate strings in the first place.

The instinct when you see that ratio is to reach for a cheaper generative model instead. As you will fidn out for yourself, that isn’t the fix either. A smaller generative model still produces a string, still needs parsing and validation, and still reports confidence you can't trust. It lowers the price per call and leaves the structural waste exactly where it was.

To sum it up: the waste is in the interface, not the invoice.

A classification call, two ways

Here's the same routing decision implemented the two ways. First, the generative approach that most of my own early pipelines used:

import json

def route_ticket_llm(ticket: str, client) -> tuple[str, float]:
    """Ask a chat model to route a support ticket. Returns (tier, confidence)."""
    prompt = (
        "Classify this support ticket into one of: urgent, standard, low. "
        'Return JSON: {"tier": "...", "confidence": 0.0-1.0}\n'
        f"Ticket: {ticket}"
    )
    raw = client.chat.completions.create(
        model="gpt-5.6-terra",
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content": prompt}],
    ).choices[0].message.content

    parsed = json.loads(raw)                  # can raise
    tier = parsed["tier"]                      # can be anything
    confidence = float(parsed["confidence"])   # can be nonsense
    if tier not in {"urgent", "standard", "low"}:   # your schema, enforced by you
        tier = "standard"                      # a guess on the failure path
    return tier, confidence

Now the System One version, using the actual TypeSafe SDK shape:

from typesafe_sdk import Choice, TypeSafeClient

client = TypeSafeClient(api_key="...")

def route_ticket_jev(ticket: str) -> tuple[str, float]:
    """Same decision. Typed from the start, one parallel pass."""
    res = client.system_one(
        questions={
            "tier": Choice(
                instructions="route the ticket",
                criteria={
                    "urgent": "revenue lost or service down",
                    "standard": "needs a person today",
                    "low": "can wait",
                },
            ),
        },
        model="jev-1.13.0",
        state={"ticket": ticket},
    )
    choice = res.choices["tier"]
    return choice.choice, choice.confidence

You’ll notice that the second version has no parse step, no validation step, and no failure path where the model returns a value you didn't allow. The schema was part of the request, so the contract is enforced before the call rather than after it (usually through a Pydantic schema validation component).

The difference that matters most is what happens with an ambiguous ticket. In the first version, confidence is a string the model made up. In the second, it's a number you can trust enough to branch on:

tier, confidence = route_ticket_jev(ticket)

if confidence < 0.7:
    tier = escalate_to_human(ticket)   # Jev says it's not sure. Trust that.

That branch is the whole automation argument in one line. When the model can tell you it's uncertain, you can route the uncertain cases to a human and let the confident ones run unattended. The model doesn't need to be right every time. It needs to be honest about when it isn't (very critical for pipelines that need to make decisions on unclear inputs), and then the system around it becomes reliable even though the model isn't.

This isn't hypothetical for me. My own news filter uses a small Jev call to decide keep or drop before spending a full LLM on anything worth reading. A logged run came back at 354 input tokens and a probability, total. That's the point in miniature. The expensive model never sees the boring stuff.

The role is specific, and the stack keeps the big model

Nothing here argues against generative models. They're for open-ended reasoning and generation, and nothing replaces them there. The argument is about the division of labor inside an LLM operation: the big model thinks and writes, and the decision points around it run on something shaped like a function call. LangChain's framing is exactly right when it suggests using an LLM for open-ended reasoning and generation, and Jev for fast, structured decisions along the way.

The early deployments show the pattern. LangChain's Open SWE router was the first version anyone could read. It originally classified requests with an LLM using structured output, then switched to Jev, which made classification almost 50 times faster. In the A/B test that mattered, routing 973 agent threads across model tiers cut the median cost per thread 64%, from $2.61 to $0.94, with no measurable quality change. The same people also ran the opposite experiment, routing everything to the cheapest model, and killed it within a day because engineers said output quality was disrupting their work. That experiment is why cheapness was never the objective. The objective was fitting the tool to the task.

The guardrail pattern is the one I expect to spread. Coding harnesses like Claude Code and Cursor already classify dangerous actions before taking them, but the classifier lived in their closed-source code. A cheap, calibrated decision model lets any agent apply the same gate before a tool execution by asking Jev if the call is risky, and block it if the answer is yes. LangChain shipped exactly that as Auto Mode middleware over Jev.

None of this requires believing TypeSafe's biggest numbers, and you shouldn't take them at face value. The workflow-eval claims of 193.6x faster and 444.6x cheaper come from the vendor's own evaluations, built by its own team, scored against models the vendor chose. The intelligence-parity claim is only about System One shaped tasks, not general capability.

What you can verify yourself is the price, the latency on your own calls, and the schema guarantee, which is falsifiable by a single bad response. Treat the launch numbers as the ceiling, measure your own workload, and expect the real ratio to land somewhere between 40x and 400x. That's still a big number, and it doesn't depend on marketing.

Why "rise" is the right word

The name Jev comes from William Stanley Jevons, the economist who noticed that making steam engines more efficient increased the demand for coal rather than reducing it. Cheaper steam meant more uses for steam. TypeSafe's bet is that machine intelligence follows the same path where every order of magnitude drop in the cost of intelligence unlocks orders of magnitude more use cases. Their own Doom demo runs about ten queries a second, which they estimate costs around seven dollars an hour, and their reaction was that this was cheaper than expected. A few years ago that sentence would not have existed.

That's the rise. The price and the interface put decisions inside ordinary code paths for the first time. The chatbot race never did that. When a routing decision costs a fraction of a cent and answers in a hundred milliseconds, you stop treating AI as a service you call for special occasions and start treating it as an if-statement that happens to be learned. Projects involving decision-making at scale, such as the map-reduce over a petabyte of unstructured data, or the email triage that never sleeps never made sense at frontier prices with prose responses. They make sense at $0.042 per million input tokens with typed outputs.

Software was never waiting for a model that could write better. It was waiting for a model that could decide, cheaply enough and honestly enough to be trusted with the boring work. The big generative models will keep getting better at thinking and writing. The decisions in between will increasingly be made by models that don't write at all.
